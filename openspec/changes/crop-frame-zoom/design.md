# Design

## Context

Рамка обрезки (ADR-0045) ставится на сцене строки сборки: `locus.js`
(`openStage`, `listenForFrame`) кладёт в строку `.crop-canvas` с картинкой
страницы черновика и `.crop-frame`, пишет доли «л;в;ш;в» в скрытое поле
`…Crop`. Картинку отдаёт `GET /problems/drafts/{id}/pages/{page}`
(`AssemblyDraftController.page` → `AssemblyDraftService.preview` →
`PdfAssembly.preview`): длинная сторона не больше 1600 px, страница PDF —
не больше 150 dpi. Сцена ужата до `max-height: 80vh`, на ней
`touch-action: none` — любое касание рисует, и каждое `pointerdown`
начинает рамку заново.

Отрисовка страниц для страницы просмотра (`ru.locus.file.PdfPages`,
`pdf-pages-as-images`) — отдельная, без масштаба: её не трогаем.

## Goals / Non-Goals

**Goals:**

- Страницу на сцене можно увеличить и прокрутить пальцем, не теряя
  рисования рамки пальцем.
- Готовую рамку можно поправить за угол или сторону.
- При 300 % страница не мылится: на CSS-пиксель сцены приходится
  не меньше пикселя картинки на типичном планшете.
- Обычный показ не тяжелеет: телефон без увеличения качает прежние
  сотни килобайт.

**Non-Goals:**

- Масштаб щипком: жест конфликтует с рисованием пальцем, а «−/+»
  владелец выбрал явно (карточка, вариант (а)).
- Перетаскивание рамки целиком: ручек на углах и сторонах хватает
  для уточнения границы; при нужде — отдельная работа.
- Масштаб на странице просмотра файла (`file/viewer.html`).

## Decisions

### Где живут данные

Новых данных нет. Крупная картинка страницы — производное от черновика,
вычисляется по запросу и не хранится. Черновик — данные инструмента
общей библиотеки, принадлежащие загрузившему Администратору (ADR-0044);
показ, в том числе крупный, идёт через `AssemblyDraftService.preview`
с `UserId` из `CurrentUser`: чужой черновик и страница вне его — 404,
как прежде. Менять показ ничего не может.

### 1. Размер крупного показа — параметр, а не поднятый предел

Под вопросом было: поднять общий предел показа или завести второй размер
по параметру. Выбран **параметр** `large` (`?large=true`) с двумя
фиксированными размерами: обычный — прежние 1600 px / 150 dpi, крупный —
3200 px по длинной стороне и не больше 300 dpi у страницы PDF; картинка
по-прежнему не увеличивается сверх своего размера.

Почему: страница A4 при 3200 px весит около мегабайта и рисуется
заметно дольше, а нужна только тому, кто увеличил масштаб. Скрипт
запрашивает крупную картинку при первом масштабе больше 100 % и дальше
держит её; без увеличения телефон качает прежнее. Размер не
произвольный (не число пикселей в параметре), чтобы запрос не мог
заставить сервер рисовать страницу любого размера.

3200 px выбраны по признаку готовности «при 300 % не мылится»: сцена
на планшете при 100 % — около 800 CSS px по длинной стороне страницы,
при 300 % — около 2400, и 3200 px картинки дают больше пикселя на
CSS-пиксель. 300 dpi — разрешение сканирования (`SCAN_DPI`), выше
у исходника деталей нет.

Отвергнуто: поднять предел для всех — показ на телефоне тяжелеет вчетверо
без пользы; отдавать исходник как есть — фото с телефона весит мегабайты,
PDF браузер на Android не рисует.

Кэш тот же — `private, max-age=1h`: содержимое черновика неизменно,
у крупной картинки свой адрес.

### 2. Масштаб — ширина сцены, ступени 100–400 %

Сцена: панель (`−`, подпись «100 %», `+`, переключатель режима), под ней
окно `.crop-viewport` с `overflow: auto` и прежним пределом высоты
`80vh`, в окне `.crop-canvas`. При 100 % картинка вписана в окно, как
сейчас; при большем масштабе скрипт задаёт `.crop-canvas` ширину
«вписанная ширина × масштаб», картинка тянется на 100 % ширины.
Ступени — 100, 150, 200, 300, 400 %. После смены масштаба окно
прокручивается так, чтобы середина видимого места осталась на месте.

Рамка и ручки позиционируются в процентах от `.crop-canvas`, поэтому
масштаб их не сбивает, а доли считаются от прямоугольника
`.crop-canvas` — как и раньше.

### 3. Режим «Рисовать | Двигать» — переключатель, по умолчанию «Рисовать»

Под вопросом было: переключать режим явно или угадывать (например,
двигать одним пальцем, рисовать — после долгого нажатия). Выбран явный
переключатель (вариант владельца в карточке): угадывание жестов
на планшете ошибается, а ошибка здесь — испорченная рамка.

«Рисовать» — по умолчанию, как сейчас: без увеличения прокручивать
нечего. В «Двигать» у `.crop-canvas` `touch-action: pan-x pan-y` —
палец прокручивает окно силами браузера (с инерцией); мышь тянет
страницу — скрипт сдвигает прокрутку окна. В «Рисовать» —
`touch-action: none`, как прежде; прокрутка окна — полосами прокрутки.

### 4. Ручки — восемь, тянутся в любом режиме

На углах и серединах сторон рамки — ручки `.crop-handle` с полем касания
не меньше 28 px (видимый квадрат меньше). У ручки `touch-action: none`
и свои события: нажатие на ручку не начинает новую рамку и не прокручивает
страницу даже в «Двигать». Угол двигает две стороны, сторона — одну;
перетянутая через противоположную сторону рамка выворачивается
(нормализуется min/max), рамка не выходит за страницу и не схлопывается
мельче прежнего порога 0,5 %.

### 5. Без скрипта — без изменений

Кнопки масштаба и ручки строит скрипт; без него сцены нет, строка берёт
страницы целиком (`problem-pdf-assembly`, «Страница черновика
показывается картинкой»).

## Risks / Trade-offs

- [Крупная картинка тяжела на мобильном интернете] → запрашивается
  только при увеличении и кэшируется браузером на час.
- [Отрисовка PDF на 300 dpi дольше] → одна страница за раз и по явному
  действию; страница A4 векторная рисуется долями секунды.
- [Две картинки одной страницы] → при смене обычной на крупную рамка
  не прыгает: доли не зависят от размера картинки.

## Migration Plan

Не нужен: данных и схемы нет, адрес прежний, параметр необязательный.
