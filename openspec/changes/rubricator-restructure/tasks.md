## 1. Вопрос дерева расширяется до переноса и счёта

- [ ] 1.1 Дополнить интерфейс `ru.locus.taxonomy.NodeContent` двумя методами
      с реализациями по умолчанию: `moveTopicContent(TaxonomyNodeId from,
      TaxonomyNodeId to)` — перевесить своё содержимое узла `from` на `to`,
      по умолчанию не делать ничего; `countVanishing(TaxonomyNodeId node)` —
      сколько своего исчезнет невосполнимо вместе с узлом, по умолчанию `0`.
      В javadoc обоих записать, кто обязан их переопределить и почему
      (design.md, «Перевешивание метки — операция области Задач»); у
      `countVanishing` — что наружу отдаётся **только число**, без владельца
      и без значений, и что отсутствие фильтра по владельцу здесь намеренное
      (ADR-0005, ADR-0027). Проверка: `mvn test -Dtest=TheoryServiceTest`
      зелёный — теория ни один из методов не переопределяет и от расширения
      интерфейса не ломается.
- [ ] 1.2 Переопределить `moveTopicContent` в `ru.locus.problem.ProblemsOnNode`
      вызовом нового метода `ProblemService` (раздел 2), `countVanishing`
      оставить нулевым с javadoc «Задачи не исчезают — они распределяются».
      В `ru.locus.theory.TheoryOnNode` явно записать в javadoc, что теория
      в переезде не участвует: материал законен на любом узле, а узел
      со своими материалами не снимается ни одной операцией перестройки
      (ADR-0033). Проверка: `mvn test -Dtest=TaxonomyServiceTest` зелёный.
- [ ] 1.3 Тест долга `MasteryRestructureDebtTest` в `src/test/java/ru/locus/taxonomy/`
      по образцу `ProblemUsageDebtTest` и `DeletionCheckDebtTest`: перечисляет
      реализации `NodeContent`, утверждает, что отвечающего по существу
      на `countVanishing` сегодня нет, и падает с внятным текстом, когда
      область отметок Владения появится, но вопрос переопределить забудет.
      Проверка: тест зелёный сегодня; в его тексте назван элемент бэклога
      `mastery-marks`.

## 3. Углубление Темы с Темой-приёмником

- [ ] 3.1 Заменить в `TaxonomyService.create` безусловный
      `refuseIfDeepeningLosesContent` на условный: перегрузка
      `create(String name, TaxonomyNodeId parent, TaxonomyNodeId receiver)`,
      где `receiver` — Тема-приёмник. Если у родителя есть содержимое,
      требующее Темы, а `receiver` не указан — прежний отказ
      `TopicCarriesContentException` с новым текстом «нужно указать
      Тему-приёмник». Прежняя двухаргументная `create` остаётся и зовёт
      новую с `null`. Проверка: `TaxonomyServiceTest` — потомок у Темы
      с Задачами без приёмника отклоняется, у Темы без Задач создаётся
      по-прежнему.
- [ ] 3.2 Ввести проверку приёмника по состоянию дерева **после** операции
      (design.md, «Проверка „приёмник — Тема“»): законен создаваемый потомок
      (обозначается отдельным значением, а не идентификатором — его ещё нет)
      и любой существующий узел без потомков, кроме углубляемой Темы.
      Отказ — своим исключением с внятным текстом. Проверка:
      `TaxonomyServiceTest` — приёмником указана сама углубляемая Тема:
      отказ, потомок не создан; приёмником указан Раздел: отказ.
- [ ] 3.3 Выполнить переезд в одной транзакции с созданием потомка: создать
      узел, затем позвать `moveTopicContent(углубляемая, приёмник)` у каждой
      реализации `NodeContent`. Порядок именно такой — приёмником может быть
      только что созданный узел. Проверка: `TaxonomyServiceTest` — после
      углубления все Задачи прежней Темы размечены приёмником, прежняя Тема
      Задач не несёт и её вид — Раздел; при отказе на любом шаге узел
      не создан и разметка не тронута.
- [ ] 3.4 Тест `TaxonomyKnowsNothingOfProblemsTest` дополнить: в исходниках
      `TaxonomyService` не встречается ни `ProblemService`, ни `problem_topic`
      — переезд идёт только через `NodeContent`. Проверка: тест зелёный.
