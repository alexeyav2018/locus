## Context

`PdfAssembly.imagePage` (`PdfAssembly.java:578`) вкладывает JPEG байт в байт
(`JPEGFactory.createFromByteArray`), затем читает ориентацию
`orientationOf` (`:626`) через `ExifUtils.getExifOrientation` Thumbnailator,
который зовёт `JPEGImageReader.getImageMetadata`. Встроенный чтец Java
строит дерево метаданных JFIF и на файле с JFIF-маркером и каналами 0, 1, 2
(так пишет камера Android-планшета) отвечает `IIOException: Inconsistent
metadata read from stream`. `orientationOf` ловит `IOException` и бросает
отказ «не разбирается».

Показ страницы черновика (`imagePreview`, `:194`) и обрезка рамкой
(`imagePiece`, `:385`) читают картинку через Thumbnailator, который ту же
ошибку пропускает и считает картинку неповёрнутой.

Данные — общая библиотека: сборка PDF Задачи, ведёт Администратор,
фильтра по владельцу нет (черновик сборки принадлежит загрузившему,
как и прежде). Модель данных и права не меняются.

## Goals / Non-Goals

**Goals:**
- JPEG без читаемых сведений о съёмке собирается целиком, без перекодирования.
- Повёрнутый снимок со сведениями EXIF по-прежнему разворачивается.
- Неразбираемый JPEG по-прежнему отклоняется.

**Non-Goals:**
- Журнал причин отказа — элемент `assembly-refusal-cause`.
- Свой разбор сегмента APP1/Exif.

## Decisions

**Нечитаемые сведения о съёмке — ориентация «как хранится».** Под вопросом
было, что делать при ошибке чтения метаданных. Варианты из карточки бэклога:
(а) считать `TOP_LEFT` и вкладывать; (б) разбирать сегмент APP1/Exif
самостоятельно мимо ImageIO; (в) перекодировать через Thumbnailator.
Выбран (а) — предпочтительный в карточке: так ведут себя показ и обрезка,
результат совпадает с показанным Администратору; (б) — свой разборщик EXIF
ради файлов, где EXIF нет; (в) нарушает «без пережатия» ADR-0044.

**Разбираемость проверяется на самой картинке, а не на метаданных.** Под
вопросом было, не служил ли `orientationOf` заодно проверкой «файл — JPEG»
и не превратит ли правка отказ во вложение битой картинки. Проверено тестом
`brokenJpegIsRefused`: нет — испорченный заголовок роняет уже
`JPEGFactory.createFromByteArray`, а `orientationOf` до него не доходит.
Но падал `JPEGFactory` исключением `IOException`, которое `assemble`
оборачивает в `UncheckedIOException` «Не удалось собрать PDF» — страница
ошибки вместо отказа с именем файла. Варианты: оставить как есть (вне
карточки) либо отклонять так же, как неразбираемый PNG. Выбрано второе:
предложение обещает «неразбираемый JPEG отклоняется», и после правки это
единственное место, где JPEG может оказаться неразбираемым; правка — одна
обёртка, симметричная ветке PNG.

**Без записи в журнал приложения.** Падение чтения метаданных — штатная
ветка, а не отказ: результат правильный, Администратору сообщать нечего.
Журналирование отказов — предмет `assembly-refusal-cause`.

## Risks / Trade-offs

- [Снимок, у которого EXIF есть, но метаданные не читаются по иной причине,
  ляжет неповёрнутым] → так же он выглядит при показе и обрезке; Администратор
  видит это до сборки и может повернуть исходник. Принятая цена варианта (а).
