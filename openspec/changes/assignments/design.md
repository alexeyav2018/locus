## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь только то, что
определяет устройство.

Задание — вторая область личного контура, и строится она по готовому
образцу первой: `ru.locus.student` (`StudentRepository.java:36` — `UserId`
в каждом методе; `StudentService.java:30` — `@PreAuthorize("hasRole('TEACHER')")`
на каждой операции, владелец из `CurrentUser`; чужое неотличимо
от несуществующего через `@ResponseStatus(NOT_FOUND)`). Что нового
по сравнению с ней:

- **Область ссылается на библиотеку** (`problem`, `theory`, `taxonomy`)
  и на личное (`student`) — все зависимости вниз, ни одной обратной.
  Обратные — только вопросами, и оба вопроса уже объявлены и ждут ответа:
  `ProblemUsage` (`ProblemUsage.java:38`) и `StudentUsage`
  (`StudentUsage.java:40`); каждый со своим тестом долга.
- **Ответ на `ProblemUsage` считает Задания всех Учителей** — метод
  репозитория без `UserId`, второй в системе после `countVanishing`.
  Оформляется по [ADR-0036](../../context/adr/0036-voprosy-biblioteki-bez-vladelca.md).
- **Появляется время.** «Не сдано» — первое вычисление, зависящее
  от «сегодня»; бина `Clock` в приложении нет
  (`FileStorageConfiguration.java:37` создаёт свой на месте).
- **Появляется собственный вопрос** к ещё не построенной области:
  «есть ли Работа по Заданию» для `submission-review`.

Теория к Заданию считается из готового: `TheoryService.materialsOn(node)`
(`TheoryService.java:91`) уже отдаёт материалы узла вместе
с унаследованными и признаком «свой» — это ровно два охвата ADR-0018.
Наименование Задач для показа — `FoundProblem` и `ProblemService.named`
(`ProblemService.java:132`), сегодня приватный.

**Где живут данные.** Задание, Раздача и состав Задания — **личный
контур**. Владелец — Учитель, колонка `user_id` во всех трёх таблицах;
выдаёт, переносит срок и удаляет только владелец с ролью Учителя. Каждый
метод обоих репозиториев принимает `UserId`, **кроме одного**,
перечисленного поимённо с причиной: `countByProblem(ProblemId)` — ответ
библиотеке по ADR-0036. Сервис берёт владельца у `CurrentUser`;
контроллер его не читает. Задачи и теория, которые Задание показывает, —
библиотека, по владельцу не фильтруются: их отдают библиотечные сервисы,
у которых параметра владельца нет.

## Goals / Non-Goals

**Goals:**

- Область `ru.locus.assignment` с полным набором слоёв; правило ADR-0027
  в форме сигнатур и тест изоляции двумя Учителями.
- Первые настоящие ответы на `ProblemUsage` и `StudentUsage`;
  заморозка Задачи и неудаляемость Ученика впервые срабатывают.
- «Не сдано» как чистая функция от Задания, часов и ответа на вопрос
  о Работах; ни одной хранимой колонки с этим смыслом.
- Вопрос `AssignmentWork` с тестом долга для `submission-review`.
- Выдача от результатов поиска без единой строки JavaScript.

**Non-Goals:**

- Работы, вердикты, отметки — следующие элементы.
- Правка состава Задания и охвата после выдачи — отклонено
  [ADR-0037](../../context/adr/0037-zadanie-neizmenno-posle-vydachi.md).
- Подбор по пробелам (С4, первый режим) — ждёт `mastery-views`.
- Выбытие ученика — долг ADR-0035, вопрос владельцу на гейте.
- Статистика по несданному сверх сводки с отбором (доли, динамика).
- Часовой пояс Учителя: «сегодня» берётся по часам сервера.

## Decisions

### Одна область `assignment` на Задание и Раздачу

`Assignment`, `AssignmentId`, `AssignmentBatch`, `AssignmentBatchId`,
`TheoryScope`, `AssignmentRepository`, `AssignmentBatchRepository`,
`AssignmentService`, `AssignmentController`, `AssignmentWork`,
`AssignmentsOfProblem` (ответ на `ProblemUsage`), `AssignmentsOfStudent`
(ответ на `StudentUsage`) — всё в `ru.locus.assignment`. Раздача без
Заданий не существует, как Группа без Учеников; два репозитория,
а не один, — сущности разные.

### Схема: три таблицы, владелец в каждой, составные ключи без каскада

```
assignment_batch                 assignment
  id            PK                 id                    PK
  user_id       FK user_           user_id               FK user_
  group_name    text               student_id            FK (student_id, user_id)
  issued_on     date                                      -> student(id, user_id)
  uq (id, user_id)                 assignment_batch_id   NULL; FK (batch_id, user_id)
                                                          -> assignment_batch(id, user_id)
                                   issued_on             date
                                   due_date              date
                                   theory_scope          text
                                   uq (id, user_id)

assignment_problem
  assignment_id  FK (assignment_id, user_id) -> assignment(id, user_id) CASCADE
  problem_id     FK problem(id), без каскада
  user_id
  position       int
  PK (assignment_id, problem_id)
```

Ключи на `student` и на `assignment_batch` — составные с `user_id`, как
`group_student` (`0006-students-groups.yaml`, третий changeset): Задание
чужому Ученику **не может существовать** — ему не на что сослаться.
Оба без каскада: Ученик с Заданием не удаляется по ADR-0035, а Раздача
удаляется сервисом вместе с Заданиями явно, в одной транзакции. Ключ
на `problem` без каскада: Задача, вошедшая в Задание, заморожена
(ADR-0030), и удалить её база не даст даже в обход сервиса. Каскад один —
состав от Задания: состав — часть записи, а не суждение, как членство
в Группе.

Раздача хранит **имя Группы текстом**, а не ключ на `group_`: Группа
удаляется в любой момент (ADR-0035), и ключ либо запретил бы это, либо
обнулялся бы, теряя происхождение. Имя на момент выдачи — исторический
факт, а не производные данные.

Срок и охват лежат на Задании, а не на Раздаче: Раздача — «лёгкая
сущность, помнит происхождение, не более» (ADR-0016), а срок у Задания
переносится по одному.

`position` — порядок Задач в Задании: учитель выбирает их в порядке,
который для него что-то значит, и список без порядка перемешался бы
от чтения к чтению.

### «Не сдано» — функция в сервисе от трёх входов

```
notSubmitted(assignment) = today(clock) > dueDate
                        && !works.withWork(ids).contains(assignment.id)
```

`today` — `LocalDate.now(clock)` с бина `Clock` (`ru.locus.TimeConfiguration`,
`Clock.systemDefaultZone()`). Один бин на приложение, а не второй
`Clock.systemUTC()` рядом с хранилищем: хранилищу нужен момент, здесь —
календарная дата, и вторые часы разошлись бы с первыми на границе суток.
Хранилище не трогается: его часы внутренние.

Вычисляется в сервисе при каждом показе, для списка — одним вопросом
на весь список (`withWork(Collection<AssignmentId>)`), а не по одному.
«Только несданные» отбирается в сервисе после чтения, а не в SQL:
условие зависит от ответа чужой области, которого в SQL нет.

В тестах — `TestClock` (`@Component @Primary` в тестовых исходниках,
как `TestLibrary`): часы со сдвигом, который тест ставит и снимает;
контекст один на все тесты, второй не поднимается.

### Вопрос `AssignmentWork`: один метод, ответчик — `submission-review`

```java
public interface AssignmentWork {
    /** Задания из перечисленных, по которым есть хотя бы одна Работа. */
    Set<AssignmentId> withWork(Collection<AssignmentId> assignments);
}
```

Владельца в вопросе нет — как у `StudentUsage`: ответчик личный,
и владельца он берёт у `CurrentUser` сам. Один метод на оба употребления —
вторая половина «не сдано» и отказ в удалении; второй метод
«опиши, что держит» забыли бы реализовать вместе с первым. Сообщение
отказа собирает область Заданий: «по Заданию уже есть Работа».
Реализаций сегодня нет, множество пусто; тест долга
`AssignmentWorkDebtTest` по образцу `ProblemUsageDebtTest`.

### Ответы на вопросы: `ProblemUsage` без владельца, `StudentUsage` с владельцем из `CurrentUser`

`AssignmentsOfProblem implements ProblemUsage` → `countByProblem(ProblemId)`
по всем Учителям, ответ «вошла в Задания (N)». Метод без `UserId` —
в поимённом списке `OwnerIsRequiredByAssignmentsTest` с причиной ADR-0036.
`AssignmentsOfStudent implements StudentUsage` → `countByStudent(owner,
student)` с владельцем из `CurrentUser`: спрашивает `StudentService`
от имени вошедшего, чужого Ученика он и не найдёт. Оба зависят только
от репозитория, не от `AssignmentService`, — цикла бинов нет
(`ProblemService` собирает `List<ProblemUsage>`, `StudentService` —
`List<StudentUsage>`).

Пояснение `NodeContent.countVanishing` о «единственном исключении»
правится: с ADR-0036 их класс.

### Теория — из `materialsOn` по Темам Задач, без своего обхода

Темы всех Задач Задания — объединение `Problem.topics()`. Охват
`TOPICS`: `materialsOn(topic)` для каждой, берутся только `own`.
`TOPICS_AND_SECTIONS`: то же, берётся всё. Дубли по идентификатору
материала снимаются с сохранением первого вхождения. Своего подъёма
по предкам не заводится (standards.md, «Данные»: подъём один на проект),
и нового метода у `TheoryService` тоже: N вызовов по числу Тем —
единицы. `NONE` — список не считается вовсе.

### Выдача: адресат ровно один, две операции сервиса

`Addressee` — запечатанный тип `ToStudent(StudentId)` | `ToGroup(GroupId)`
с фабрикой `Addressee.of(Long student, Long group)`, отказывающей на
«ни одного» и «оба». Правило живёт в типе области, контроллер лишь зовёт
фабрику и раскладывает по двум методам: `issueToStudent(StudentId,
List<ProblemId>, LocalDate, TheoryScope) → AssignmentId` и
`issueToGroup(GroupId, …) → AssignmentBatchId`. Один метод с двумя
необязательными параметрами дал бы ветвление внутри и неясный тип
ответа.

`issueToGroup` — одна транзакция: Раздача, затем Задание на каждого
члена Группы через `GroupService.members`; пустая Группа — отказ до
записи. Задачи проверяются одним чтением `ProblemService.problems(ids)`
(новый публичный метод: `findByIds` в репозитории и уже существующий
`named`), отсутствующая — отказ. Повторы снимаются с сохранением порядка.

### После выдачи: перенос срока, удаление через одну проверку

`changeDueDate(AssignmentId, LocalDate)` — единственная правка.
`delete(AssignmentId)` и `deleteBatch(AssignmentBatchId)` идут через
отдельный названный метод `refuseUnlessNoWork(List<Assignment>)`,
спрашивающий `AssignmentWork` одним вызовом на весь список; Раздача
удаляется целиком или отклоняется целиком (ADR-0037). Флага «удалить
без проверки» нет (antipatterns.md).

### Экраны

- `GET /problems` — у каждой найденной Задачи отметка, под списком кнопка
  «Выдать отмеченные» → `GET /assignments/new?problem=…`. Показывается
  только Учителю: `ProblemSearchController` кладёт `teacher`, как
  `HomeController`. Результаты уже вне формы поиска, вторая форма
  вложенности не создаёт; метод `GET` — переход к форме, а не действие.
- `GET /assignments/new` — форма: выбранные Задачи (номер, подпись,
  разметка — `FoundProblem`), срок `<input type="date">`, охват теории
  радиокнопками, адресат: Ученик (`select`) либо Группа (`select`).
- `POST /assignments` — выдача; после — на страницу Задания или Раздачи.
- `GET /assignments` — сводка с отбором: Ученик, Раздача, период срока,
  «только несданные»; условия в адресе, форма `GET`, как у поиска.
- `GET /assignments/{id}` — Задание: Ученик, даты, «не сдано», состав
  со ссылками на `/problems/{id}`, теория по охвату со ссылками
  на `/theory/{id}`, форма переноса срока, удаление.
- `GET /assignments/batches/{id}` — Раздача: имя Группы, дата, Задания
  по Ученикам с «не сдано», удаление Раздачи.
- Карточка Ученика — ссылка «Задания Ученика» на `/assignments?student=…`:
  только адрес в шаблоне, `student` о `assignment` в коде не узнаёт.
  Главная — ссылка «Задания» под `teacher`.

Даты показываются в `dd.MM.yyyy` через `#temporals`; фразы, которые
человек видит слитно, — в одном `th:text`.

### Тесты формы и изоляции

`OwnerIsRequiredByAssignmentsTest` — своя область, свой тест, по образцу
`OwnerIsRequiredByStudentsTest`, но с поимённым списком исключений:
`AssignmentRepository.countByProblem` с причиной ADR-0036. Все прочие
публичные методы обоих репозиториев принимают `UserId`; таблицы
`assignment_batch`, `assignment`, `assignment_problem` несут `user_id`.

`AssignmentsAreFilteredByOwnerTest` — HTTP двумя Учителями: список,
прямой адрес Задания и Раздачи, перенос срока, удаление, выдача чужому
Ученику и чужой Группе; обратная половина — одна Задача в Заданиях обоих.
Репозиторные тесты — каждый метод с двумя владельцами.

`NotSubmittedIsNotStoredTest` — поимённый состав колонок трёх таблиц,
как `StudentIsNotAUserTest`: миграция, добавившая «сдано», уронит тест.

## Risks / Trade-offs

**`countByProblem` без владельца — первый метод личного репозитория,
который компилятор не защищает** → поимённый список в тесте формы
с причиной; метод отдаёт `int`, не записи; ADR-0036 запрещает второй
вид методов без владельца.

**Раздача помнит имя Группы, а Группа переименована** → это по замыслу:
Раздача — исторический факт выдачи «9Б» такого-то числа, а не ссылка;
записано в спеке сценарием.

**Срок без ограничений — опечатка в году даёт мгновенное «не сдано»** →
ошибка видна сразу в сводке, а не тихая; срок переносится свободно.
Запрет на прошлое отверг бы честную запись «выдал вчера, записываю
сегодня».

**Теория к Заданию меняется после выдачи** → следствие ADR-0018
и ADR-0033, записано в ADR-0037; ученику передаётся вне системы.

**«Сегодня» по часам сервера** → один Учитель, один сервер, один пояс;
пояс задаётся окружением при развёртывании (`deployment-backup`).

**N вызовов `materialsOn` по числу Тем** → Тем в Задании единицы,
запрос дешёвый; общий метод на набор узлов завёл бы второй порядок
обхода.

**`ProblemSearchController` начинает знать роль вошедшего** → только
флаг для показа отметок, как `HomeController`; поиск для всех прежний.

## Migration Plan

Одна миграция `0007-assignments.yaml`, три changeset'а в порядке ключей:
`assignment_batch`, `assignment`, `assignment_problem`. Данных к переносу
нет, обратной совместимости не требуется
([ADR-0024](../../context/adr/0024-obnovlenie-s-ostanovkoj.md)).
