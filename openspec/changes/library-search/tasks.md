## 1. Условия поиска и отбор в хранилище

- [x] 1.1 Завести перечисление `MatchMode` в `ru.locus.problem`: `ALL`
  («все сразу») и `ANY` («любое из»), с методом `title()` по образцу
  `ExamPart`. Javadoc: почему русское имя живёт здесь, а не в шаблоне.
  Проверка: `MatchModeTest` — у каждого значения непустое русское имя,
  значений ровно два.
- [x] 1.2 Завести запись `ProblemFilter` в `ru.locus.problem`: `node`,
  `methods` + `methodMode`, `characteristics` + `characteristicMode`, `part`.
  Компактный конструктор приводит `null`-список к пустому, а `null`-режим —
  к `ANY`, чтобы дальше по коду не было двух способов сказать «ничего
  не выбрано». Добавить `boolean isEmpty()`. Проверка: `ProblemFilterTest` —
  пустой Фильтр считает себя пустым; Фильтр с одним значением — нет;
  `null`-список становится пустым; `null`-режим становится `ANY`.
- [x] 1.3 Расширить `TestLibrary`: `topic(TaxonomyNodeId parent)` — Тема
  под указанным узлом (нужна для проверки обхода поддерева на глубину) —
  и `problem(...)` с полной разметкой (Темы, Методы, Характеристики, Часть),
  чтобы тесты поиска могли строить обстановку, различимую по каждому условию
  и по каждому режиму. Проверка: существующие тесты, пользующиеся
  `TestLibrary`, продолжают проходить (`mvn test -Dtest=ProblemRepositoryTest`).
- [x] 1.4 Добавить `ProblemRepository.search(List<TaxonomyNodeId> topics,
  List<SolutionMethodId> methods, MatchMode methodMode,
  List<CharacteristicId> characteristics, MatchMode characteristicMode,
  ExamPart part)`: условия складываются подзапросами `exists` и сравнением
  колонки `exam_part`; `ANY` даёт один `exists` с `in (...)`, `ALL` — по
  одному `exists` на значение (design.md, «Отбор — `exists`»); незаданное
  условие в текст запроса не попадает вовсе; порядок — по `p.id`. Разметку
  не дочитывать (это 1.7). **Пустой список — это отсутствие условия,
  а не условие из пустого набора**, и режим при нём не смотрится; пустой
  список Тем при заданном узле невозможен и даёт
  `IllegalArgumentException`. Проверка: тесты 1.5 и 1.6.
- [x] 1.5 `ProblemSearchRepositoryTest` — на отбор: каждое условие по отдельности;
  два условия вместе отбирают пересечение; Задача, размеченная двумя Темами
  из переданного списка, возвращается один раз; пустой список Тем даёт
  `IllegalArgumentException`; порядок по возрастанию номера. Проверка:
  `mvn test -Dtest=ProblemRepositoryTest`.
- [x] 1.6 `ProblemSearchRepositoryTest` — на режимы соединения: два Метода при
  `ALL` возвращают только Задачу с обоими; те же два при `ANY` — обе Задачи,
  и Задача с обоими Методами приходит один раз; режимы у Методов
  и Характеристик работают независимо друг от друга; на одном выбранном
  значении `ALL` и `ANY` дают одно и то же; **пустой список при `ALL` и при
  `ANY` даёт один и тот же результат — тот же, что без условия вовсе**.
  Последний пункт — не формальность: механически собранный запрос вернул бы
  здесь пусто при `ANY`. Проверка:
  `mvn test -Dtest=ProblemSearchRepositoryTest`.
- [x] 1.7 Добавить дочитывание разметки пачкой: три запроса
  `where problem_id in (...)` и раскладка по Задачам в Java, чтобы число
  запросов не зависело от числа найденных (design.md, «Разметка результата
  дочитывается пачкой»). Существующие `findById` и `findByTopic` не трогать.
  Проверка: тест `ProblemSearchRepositoryTest`, где у найденных Задач разная
  разметка и каждая приходит своей.

> **Отступление от плана, раздел 1.** Тесты отбора вынесены в отдельный
> класс `ProblemSearchRepositoryTest`, а не дописаны в `ProblemRepositoryTest`:
> у того своя заявленная тема — «Задача читается обратно вместе с разметкой,
> список Темы, выборка Методов Темы», — и пятнадцать тестов отбора её
> размыли бы. Проверочные команды в пунктах 1.5–1.7 исправлены.
