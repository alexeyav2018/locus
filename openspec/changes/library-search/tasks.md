## 1. Условия поиска и отбор в хранилище

- [ ] 1.1 Завести запись `ProblemFilter` в `ru.locus.problem`: четыре
  необязательных поля — `TaxonomyNodeId node`, `SolutionMethodId method`,
  `CharacteristicId characteristic`, `ExamPart part`; `null` означает
  «условие не задано». Добавить `boolean isEmpty()` и javadoc с пояснением,
  почему это отдельный тип, а не четыре аргумента (design.md, «Условия поиска
  — отдельный тип»). Проверка: `ProblemFilterTest` — пустой Фильтр считает
  себя пустым, Фильтр с одним значением — нет.
- [ ] 1.2 Расширить `TestLibrary`: `topic(TaxonomyNodeId parent)` — Тема
  под указанным узлом (нужна для проверки обхода поддерева на глубину) —
  и `problem(...)` с полной разметкой (Темы, Методы, Характеристики, Часть),
  чтобы тесты поиска могли строить обстановку, различимую по каждому условию.
  Проверка: существующие тесты, пользующиеся `TestLibrary`, продолжают
  проходить (`mvn test -Dtest=ProblemRepositoryTest`).
- [ ] 1.3 Добавить `ProblemRepository.search(List<TaxonomyNodeId> topics,
  SolutionMethodId method, CharacteristicId characteristic, ExamPart part)`:
  условия складываются подзапросами `exists` и сравнением колонки
  `exam_part`, незаданное условие в текст запроса не попадает вовсе, порядок
  — по `p.id`. Разметку не дочитывать (это 1.5). `null` в любом параметре —
  условие не задано; **пустой** список Тем — ошибка `IllegalArgumentException`,
  а не пустой результат (design.md, «Обход поддерева берётся у рубрикатора»).
  Проверка: тесты 1.4.
- [ ] 1.4 `ProblemRepositoryTest` — на отбор: каждое условие по отдельности;
  два условия вместе отбирают пересечение; Задача, размеченная двумя Темами
  из переданного списка, возвращается один раз; пустой список Тем даёт
  `IllegalArgumentException`; порядок по возрастанию номера. Проверка:
  `mvn test -Dtest=ProblemRepositoryTest`.
- [ ] 1.5 Добавить дочитывание разметки пачкой: три запроса
  `where problem_id in (...)` и раскладка по Задачам в Java, чтобы число
  запросов не зависело от числа найденных (design.md, «Разметка результата
  дочитывается пачкой»). Существующие `findById` и `findByTopic` не трогать.
  Проверка: тест `ProblemRepositoryTest`, где у трёх найденных Задач разная
  разметка и каждая приходит своей.

## 2. Поиск в сервисе: обход поддерева и имена

- [ ] 2.1 Завести запись `FoundProblem` в `ru.locus.problem`: сама `Problem`
  плюс готовые имена — Темы полными путями, Методы и Характеристики именами.
  Javadoc: почему имена собираются здесь, а не в шаблоне (standards.md,
  «Слои и границы»). Проверка: класс компилируется, `get_diagnostics_for_file`
  чист.
- [ ] 2.2 Добавить `ProblemService.search(ProblemFilter filter)`: узел
  разворачивается в список Тем вызовом `TaxonomyService.subtree` (свой обход
  не заводить), несуществующий узел даёт внятный отказ, остальные условия
  уходят как есть; на выходе — `List<FoundProblem>` с именами, собранными
  из `taxonomy.paths()`, `methods.all()` и `characteristics.all()`,
  прочитанных **по одному разу**. Без `@PreAuthorize` — как остальное чтение
  библиотеки (design.md, «Прав поиску не добавляется»). Проверка: тесты 2.3.
- [ ] 2.3 `ProblemSearchTest` (сервисный, на `IntegrationTest`): отбор
  по Разделу находит Задачу, размеченную Темой тремя уровнями ниже; отбор
  по Теме соседние Темы не захватывает; Задача из другой ветви не попадает;
  пустой Фильтр возвращает и ту, и другую заведённую Задачу; несуществующий
  узел — отказ; имена в результате — полные пути Тем и имена записей
  словарей. Проверка: `mvn test -Dtest=ProblemSearchTest`.
- [ ] 2.4 Сторожевой тест на единственность обхода:
  `SubtreeWalkIsNotDuplicatedTest` — в исходниках области `problem` нет
  ни одного `with recursive`. Обоснование в javadoc: второй обход завёл бы
  второй предел глубины, и разошлись бы они молча (standards.md, «Данные»).
  Проверка: `mvn test -Dtest=SubtreeWalkIsNotDuplicatedTest`.

## 3. Экран поиска

- [ ] 3.1 Завести `ProblemSearchController` в `ru.locus.problem`:
  `GET /problems` с параметрами `node`, `method`, `characteristic`, `part`
  (все необязательные), модель — результаты и наполнение выпадающих списков
  (`taxonomy.paths()`, `methods.all()`, `characteristics.all()`,
  `ExamPart.values()`), выбранные значения возвращаются в форму. Контроллер
  тонкий: в репозиторий не ходит. Проверка: тесты 3.3.
- [ ] 3.2 Завести шаблон `templates/problem/search.html`: форма методом `GET`
  с четырьмя выпадающими списками (у каждого пункт «— любой —»), число
  найденных, список результатов со ссылкой на Задачу, отдельное сообщение
  «по этим условиям Задач нет». Вычислений в шаблоне не заводить. Проверка:
  тесты 3.3.
- [ ] 3.3 `ProblemSearchScreenTest` (на `IntegrationTest`, через `Browser`):
  экран открывается вошедшим Учителем; отбор по Разделу показывает Задачу
  дальнего потомка; пустые условия показывают заведённые Задачи; при пустом
  результате видно сообщение, а не пустая страница; в строке результата видны
  номер, подпись, Часть, путь Темы, имена Методов и Характеристик; выбранные
  условия остались выбранными; число найденных названо. Сравнивать видимый
  текст, а не разметку целиком (antipatterns.md). Проверка:
  `mvn test -Dtest=ProblemSearchScreenTest`.
- [ ] 3.4 Провести ссылки: строка «Задачи» в `templates/home.html` ведёт
  на `/problems`, а не на `/taxonomy`; на экране дерева
  (`templates/taxonomy/tree.html`) появляется ссылка «Искать по библиотеке»,
  ведущая на `/problems` с уже выбранным узлом. Проверка: пункт в
  `ProblemSearchScreenTest` — с экрана дерева ссылка ведёт на поиск
  с параметром `node` выбранного узла.

## 4. Граница общего и личного, слои

- [ ] 4.1 Дописать новые классы (`ProblemFilter`, `FoundProblem`,
  `ProblemSearchController`) в список `OwnerIsUnknownToProblemsTest`:
  ни один метод и ни одно поле поиска не принимает `UserId`. Проверка:
  `mvn test -Dtest=OwnerIsUnknownToProblemsTest`.
- [ ] 4.2 Дописать `ProblemSearchController` в
  `ProblemControllerIsThinTest`: контроллер поиска не держит ни репозитория,
  ни `FileStorage`. Проверка: `mvn test -Dtest=ProblemControllerIsThinTest`.
- [ ] 4.3 `SearchIsNotFilteredByOwnerTest` (на `IntegrationTest`): два разных
  Учителя входят по-настоящему и по одинаковым условиям получают один и тот же
  набор Задач; невошедший на `/problems` попадает на форму входа, а не
  на результаты. Проверка через настоящий вход, а не вызов сервиса: забытый
  фильтр не падает, а тихо показывает меньше. Проверка:
  `mvn test -Dtest=SearchIsNotFilteredByOwnerTest`.
