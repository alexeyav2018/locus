## Context

Мотивация — в [proposal.md](proposal.md), раздел «Why». Требования — в
[specs/zapusk-prilozheniya/spec.md](specs/zapusk-prilozheniya/spec.md).

Что задано снаружи и обсуждению здесь не подлежит:

- стек — Java 21, Spring, Thymeleaf, PostgreSQL ([ADR-0020](../../context/adr/0020-stek.md));
- оснастка — Maven, Liquibase, PostgreSQL в Docker Compose, Testcontainers
  ([ADR-0023](../../context/adr/0023-osnastka-sborki.md));
- слои — контроллеры тонкие, вся предметная логика и права в сервисах
  ([architecture.md](../../context/architecture.md), [standards.md](../../context/standards.md)).

Что есть на машине: Java 21.0.12, Maven 3.8.7, Docker 29.6.1. Требования
Spring Boot 4.1 — Java 17 и выше, Maven 3.6.3 и выше; обе удовлетворены.

Особенность момента: доменных таблиц нет ни одной, и в этом изменении
не появится. Поэтому решения ниже сознательно останавливаются там, где
для ответа не хватает предметного материала, — и называют, какое изменение
ответит.

## Goals / Non-Goals

**Goals:**

- Собрать каркас, к которому `auth-roles` пристраивает первую таблицу,
  не пересматривая ничего из принятого здесь.
- Сделать проверяемым машиной то, что в признаке готовности сформулировано
  словами: миграции с нуля, страница по HTTP, команды из `CLAUDE.md`.
- Задать соглашения, менять которые потом дорого: расположение кода, форма
  миграций, единая версия PostgreSQL.

**Non-Goals:**

- Выбор способа доступа к данным (JPA или JDBC) — откладывается до `auth-roles`,
  где появится первая таблица и с ней предмет для выбора.
- Выбор способа хранения дерева рубрикатора — это `rubricator-tree`
  ([architecture.md](../../context/architecture.md), раздел «Хранение данных»).
- Аутентификация, домен, HTTPS, бэкапы, боевая конфигурация — `auth-roles`
  и `deployment-backup`. Здесь фиксируется только **форма** миграций, вытекающая
  из [ADR-0024](../../context/adr/0024-obnovlenie-s-ostanovkoj.md); сама
  процедура обновления — там.
- Оснастка тестов апгрейд-пути — отложена [ADR-0023](../../context/adr/0023-osnastka-sborki.md).

## Decisions

### Spring Boot 4.1, зависимости добавляются по мере надобности

Берётся текущая линия Spring Boot (4.1) с `spring-boot-starter-parent`:
проект новый, тянуть предыдущую линию незачем — её поддержка закончится раньше.

Стартеры подключаются только те, без которых не выполнить требования:
web, thymeleaf, jdbc (ради `DataSource`), liquibase; `spring-boot-docker-compose`
и `spring-boot-testcontainers` — в области разработки и тестов соответственно.
Это не аскеза: каждый лишний стартер приносит автоконфигурацию, которая потом
срабатывает неожиданно.

*Альтернатива:* предыдущая LTS-линия 3.5. Отклонена — примеров в сети под неё
больше, но начинать новый проект с линии, которую придётся поднимать через год,
дороже. Расхождение примеров закрывается context7 (правило в `CLAUDE.md`).

### Пакет `ru.locus`, группировка по предметным областям

Артефакт — `locus`, пакет верхнего уровня — `ru.locus`, класс приложения —
`LocusApplication`.

Код группируется **по предметным областям**, слои — внутри области
(`ru.locus.<область>` содержит контроллер, сервис, репозиторий этой области).
Причина: изменение почти всегда касается одной области целиком, и при такой
группировке оно лежит в одном месте; при группировке по слоям
(`ru.locus.web`, `ru.locus.service`, …) каждое изменение размазывается
по трём далёким пакетам, а сами пакеты растут до трёх десятков классов.

Разделение слоёв от этого не страдает: оно держится на правилах
[standards.md](../../context/standards.md) и проверяется тем, что контроллер
не обращается к репозиторию, — а не тем, что классы лежат в разных папках.

*Альтернатива:* группировка по слоям. Отклонена по изложенной причине.
Соглашение записывается в `standards.md`, чтобы следующее изменение не решало
заново.

Пустых пакетов «на вырост» не заводится: в этом изменении реально появляется
одна область — стартовая страница.

### Доступ к данным: пока только `DataSource`

Каркас подключает `spring-boot-starter-jdbc` — этого достаточно, чтобы Liquibase
получил соединение, а тесты проверили состояние схемы. Ни JPA, ни `JdbcClient`
как способ писать репозитории здесь не выбирается.

Причина: выбор между ORM и прямым SQL решается свойствами доменной модели —
деревом рубрикатора с обходом поддерева, распределениями владения, разметкой
многие-ко-многим. Ни одного из этих объектов ещё нет, и выбор, сделанный
на пустом месте, будет угадыванием. Первую таблицу приносит `auth-roles` —
там и решать, записью в журнале.

### Миграции: YAML, абстрактные операции; сырой SQL — исключение

Master-changelog (`db/changelog/db.changelog-master.yaml`) подключает файлы
миграций через `includeAll` из отдельной папки в алфавитном порядке имён;
имена начинаются с номера. Каждая миграция — YAML-файл, описывающий изменение
абстрактными операциями Liquibase: `createTable`, `addColumn`, `createIndex`,
`addForeignKeyConstraint` и подобными.

Причина — автоматический откат. Для абстрактных операций Liquibase знает
обратную и генерирует её сам; для changeset'ов в формате SQL, по прямому
указанию документации, не генерирует ничего. Это единственное различие,
которое здесь чего-то стоит, и оно достаётся бесплатно
([ADR-0023](../../context/adr/0023-osnastka-sborki.md)).

Сырой SQL (`sql`-changeset) остаётся как **исключение** — там, где абстракций
не хватает: расширения PostgreSQL, `ltree` в рубрикаторе, частичные индексы,
рекурсивные обходы. В таких changeset'ах отката нет, и это нормально.

Откаты руками не пишутся ни в том, ни в другом случае. Страховка при обновлении
живой системы — архив базы перед выкаткой и починка движением вперёд; это
`deployment-backup`. Отдельно названная причина: скрипт отката, ни разу
не выполнявшийся, ломается ровно тогда, когда нужен, а структуру он вернёт
без данных.

*Альтернатива:* formatted SQL — обычный SQL с заголовками Liquibase. Отклонена:
читается лучше, но отключает автооткат целиком.

Следствие, которое надо помнить: по YAML не видно, какой SQL выполнится.
Перед выкаткой на живую базу его показывает `mvn liquibase:updateSQL`.

### Миграции пишутся под остановленную систему

Обновление живой системы проходит с остановкой
([ADR-0024](../../context/adr/0024-obnovlenie-s-ostanovkoj.md)): остановили,
сняли архив, накатили, подняли. Следствие для формы миграций — они **не обязаны
быть обратно совместимыми**: `NOT NULL`, удаление колонки, смена типа,
переименование пишутся одним changeset'ом, а не разбиваются на три выкатки ради
совместимости со старой версией приложения, которой в этот момент нет.

`CREATE INDEX CONCURRENTLY` по той же причине не используется: он не выполняется
внутри транзакции и усложняет changeset ради свойства, нужного только под
нагрузкой.

Здесь это ни к чему не применяется — миграций в изменении нет ни одной, — но
правило записывается в `standards.md` сразу, до появления первой миграции
в `auth-roles`.

### В этом изменении миграций нет ни одной

Ни одна таблица предметной области здесь не появляется, и выдумывать её ради
того, чтобы «было что мигрировать», нельзя: спека описывает поведение, а не
декорации. Поэтому папка миграций создаётся пустой, а Liquibase при старте
создаёт только свои служебные таблицы.

Следствие, которое надо назвать вслух: проверка «миграции применяются с нуля
на пустой базе» в этом изменении проверяет **механизм** — Liquibase
подключён, отрабатывает, служебные таблицы созданы, приложение стартует.
Полную силу она обретает с первым содержательным changeset'ом, то есть
в `auth-roles`.

### Разработка: приложение само поднимает базу

В корне лежит `compose.yaml` с одним сервисом — PostgreSQL с именованным томом.
Модуль `spring-boot-docker-compose` подключён в области разработки, поэтому
`mvn spring-boot:run` поднимает базу сам и сам передаёт приложению параметры
подключения: отдельного шага «сначала запусти базу» в командах не появляется,
а значит, его нельзя забыть.

Том именованный и переживает перезапуск. Это даёт вторую, бесплатную проверку
из [ADR-0023](../../context/adr/0023-osnastka-sborki.md): каждая новая миграция
накатывается на базу, где уже лежат данные предыдущей версии.

Гасить базу приложение при этом не должно: `lifecycle-management: start-only`.
Поведение по умолчанию (`start-and-stop`) гасит базу при остановке того
экземпляра, который её поднял, — и если рядом работает второй экземпляр
(запущенный на другом порту, обычная случайность при разработке), он остаётся
на умершей базе. Узнаёт он об этом не в момент причины, а при первом обращении
к данным. Плата за `start-only` — контейнер живёт до `docker compose down`
руками; это записано в `CLAUDE.md`.

В бою вопрос не возникает: экземпляр один ([ADR-0020](../../context/adr/0020-stek.md)),
и на этом же стоит порядок обновления с остановкой
([ADR-0024](../../context/adr/0024-obnovlenie-s-ostanovkoj.md)). Речь только
о локальной разработке.

### Тесты: Testcontainers, чистый контейнер, без тихого пропуска

Интеграционные тесты поднимают PostgreSQL через Testcontainers и подключают
его к контексту аннотацией `@ServiceConnection` — параметры подключения
не дублируются в конфигурации тестов.

Контейнер на каждый прогон чистый, поэтому каждый прогон и есть проверка
«с нуля на пустой базе».

Режим «пропустить тесты, если Docker недоступен» **не включается**: тест,
который молча не выполнился, хуже отсутствующего — он создаёт видимость
проверки. Нет Docker — сборка падает.

Все тесты запускаются одним раннером (surefire), деления на быстрые и
интеграционные нет: их пока единицы, а разделение стоит конфигурации, которую
придётся поддерживать.

### Версия PostgreSQL — одна, в одном месте

Единственное место — `compose.yaml`. Тесты читают версию оттуда
(`ObrazPostgres` в тестовых исходниках) и передают её Testcontainers.

Изначально предполагалось держать версию свойством сборки, но свойство Maven
до `compose.yaml` не дотягивается: Compose про `pom.xml` ничего не знает,
и «одно место» превратилось бы в два. Обратное направление работает — файл
Compose тесты прочитать могут, — поэтому источником стал он.

Разъехавшиеся версии — тихая ошибка: тесты зелёные, разработка работает,
а на боевой базе поведение другое. Та же версия потом фиксируется на VPS
в `deployment-backup`.

### Конфигурация и учётные данные

`application.yaml` в ресурсах; параметры подключения к базе при разработке
приходят от `spring-boot-docker-compose`, в тестах — от `@ServiceConnection`.
Пароль базы разработки лежит в `compose.yaml` открытым текстом: он локальный
и защищать в нём нечего. Боевые учётные данные приходят из окружения —
это `deployment-backup`, здесь их нет.

### Стартовая страница

Один контроллер, один шаблон Thymeleaf, никакого содержания: страница
подтверждает, что серверная сборка разметки работает. Она заведомо временная
и уйдёт, когда появится настоящий вход (`auth-roles`).

## Risks / Trade-offs

**Docker становится обязательным для сборки** → записывается в `CLAUDE.md`
как требование среды; падение тестов без Docker — явное, с внятным сообщением,
а не тихий пропуск.

**Spring Boot 4 моложе примеров в сети** → на расхождениях API спрашивается
context7, как предписывает `CLAUDE.md`; на память о версиях не полагаемся.

**Долгоживущая база разработки накапливает мусор** → она не является
источником истины ни для чего: все тесты идут на чистом контейнере, а базу
разработки в любой момент можно снести (`docker compose down -v`). Команда
для этого попадает в `CLAUDE.md`.

**Соглашение о группировке по областям придётся применять к пустому проекту** →
на одной области его не проверить, и первая настоящая проверка — `auth-roles`.
Если там оно окажется неудобным, менять его дешевле всего именно тогда: кода
будет полторы области.

**Отложенный выбор доступа к данным** → риск, что `auth-roles` окажется
слишком мелким предметом для решения (одна таблица пользователей ничего
не проверяет). Смягчение: решать не «под auth-roles», а с оглядкой на
`rubricator-tree` и `mastery-views`, которые и создают нагрузку на этот выбор.

## Migration Plan

Мигрировать нечего: системы нет, данных нет, пользователей нет. Откат
изменения — удаление добавленных файлов.
