## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь только то, что
определяет устройство.

Работа — третья область личного контура, и строится по образцу второй:
`ru.locus.assignment` (`AssignmentRepository` — `UserId` в каждом методе;
`AssignmentService.java:32` — `@PreAuthorize("hasRole('TEACHER')")`
на каждой операции, владелец из `CurrentUser`; чужое неотличимо
от несуществующего через `@ResponseStatus(NOT_FOUND)`). Что нового
по сравнению с ней:

- **Область — первый потребитель хранилища в личном контуре.** Файлов
  много и они изображения: пережатие по типу (образец —
  `TheoryService.stored`, `TheoryService.java:239`), порядок «сначала
  в хранилище, потом запись; при неудаче — уборка» (standards.md,
  «Файлы») — на несколько файлов за одно действие.
- **Оба вопроса, на которые область отвечает, уже объявлены и ждут:**
  `AssignmentWork` (`AssignmentWork.java:45`, `Set<AssignmentId>
  withWork(Collection<AssignmentId>)`) и `StudentUsage`
  (`StudentUsage.java:40`). `AssignmentService` уже собирает
  `List<AssignmentWork>` и спрашивает его в `notSubmitted`
  и `refuseUnlessNoWork`; `StudentService` собирает `List<StudentUsage>`
  в `refuseUnlessUnused`. Ничего в спрашивающих областях менять
  не нужно — только появиться ответчиками.
- **Загрузка с телефона.** Пределов `spring.servlet.multipart`
  в `application.yaml` нет — действуют умолчания 1 МБ на файл и 10 МБ
  на запрос. Ни один шаблон не несёт `<meta name="viewport">`.
  Тестовый `Browser.postMultipart` (`Browser.java:93`) шлёт файлы
  из `Map<String, byte[]>` с типом `application/pdf` у каждого:
  несколько файлов в одном поле и изображение через него не отправить.

**Где живут данные.** Работа и её файлы — **личный контур**. Владелец —
Учитель, колонка `user_id` в обеих таблицах; принимает, правит вердикт,
добавляет и удаляет файлы, удаляет Работу только владелец с ролью
Учителя. Каждый метод репозитория принимает `UserId` — исключений нет:
библиотека о Работах ничего не спрашивает (ADR-0036 не задействован).
Сервис берёт владельца у `CurrentUser`; контроллер его не читает.
Задачи, которые экран приёма показывает, — библиотека, отдаются
`AssignmentService.problemsOf` без владельца. Файлы Работ — персональные
данные детей: наружу только `FileStorage.temporaryLink`, ключ файла
в разметку не попадает.

## Goals / Non-Goals

**Goals:**

- Область `ru.locus.work` с полным набором слоёв; правило ADR-0027
  в форме сигнатур и тест изоляции двумя Учителями.
- Первые настоящие ответы на `AssignmentWork` и второй — на `StudentUsage`;
  «не сдано» и отказ в удалении Задания впервые срабатывают по Работе.
- Приём нескольких снимков с телефона за одно действие: пределы
  загрузки, пережатие, узкий экран.
- Пара «Задание × Задача» и единственность Работы на ней — в схеме,
  не только в сервисе.

**Non-Goals:**

- Отметки Владения и справка «решено 2 из 6» на экране приёма —
  `mastery-marks`.
- Перенос Работы на другую Задачу или другого Ученика — удалить
  и принять заново (ADR-0038).
- Просмотр изображения на странице (превью, поворот) — файл открывается
  по ссылке как есть; пережатие уже выправляет ориентацию.
- Сводка по вердиктам («сколько верных за месяц») — не первая версия.
- Приём файлов иных типов (DOCX, HEIC) — отклоняются; HEIC с iPhone
  браузер сам отдаёт как JPEG при `accept="image/*"`, а если нет —
  это обстоятельство для `deployment-backup`, не для этой работы.

## Decisions

### Одна область `work` на Работу и её файлы

`StudentWork`, `StudentWorkId`, `StudentWorkFile`, `StudentWorkFileId`,
`Verdict`, `UploadedWorkFile`, `StudentWorkRepository`,
`StudentWorkService`, `StudentWorkController`, `WorksOfAssignment`
(ответ на `AssignmentWork`), `WorksOfStudent` (ответ на `StudentUsage`),
`StudentWorkNotFoundException` — всё в `ru.locus.work`. Пакет назван
по ведущему слову, а не `studentwork`: короче и не спутывается
со `student`. Файл Работы — своя запись с идентификатором, а не строка
ключа в списке: файл удаляется поштучно, и адресовать его надо
без ключа хранилища в адресе (ключ наружу не отдаётся).

### Схема: две таблицы, владелец в каждой, пара в составном ключе

```
student_work                             student_work_file
  id             PK                        id               PK
  user_id        FK user_                  student_work_id  FK (student_work_id, user_id)
  assignment_id  NOT NULL                                     -> student_work(id, user_id) CASCADE
  problem_id     NOT NULL                  user_id          NOT NULL
  received_on    DATE NOT NULL             file_key         VARCHAR(200) NOT NULL
  verdict        VARCHAR(20) NULL          position         INT NOT NULL
  note           VARCHAR(2000) NULL
  uq (assignment_id, problem_id)
  uq (id, user_id)
  FK (assignment_id, problem_id) -> assignment_problem(assignment_id, problem_id), без каскада
  FK (assignment_id, user_id)    -> assignment(id, user_id),                     без каскада
```

Два ключа с `student_work` держат ровно два правила спеки. Ключ на
`assignment_problem` — «Задача из состава этого Задания»: Работа по Задаче,
которой в Задании нет, не вставляется и в обход сервиса. Ключ на
`assignment (id, user_id)` — «Задание этого Учителя»: Работа по чужому
Заданию не может существовать. Оба без каскада: Задание с Работой
не удаляется (ADR-0037), и база это подтвердит, если сервис забудут.
Уникальность `(assignment_id, problem_id)` — «на паре Работа одна»
(ADR-0038). Ученика в таблице **нет**: он у Задания, и вторая колонка
разошлась бы с первой; ответ `WorksOfStudent` идёт соединением
с `assignment`, как `AssignmentRepository` соединяется со `student`
(`AssignmentRepository.java:168`).

Файлы — каскадом от Работы в базе: файл без Работы — не сущность,
а забытый ключ. `position` — порядок загрузки: учитель снимает страницы
по порядку. `verdict` — `NULL` означает «не проверена»; отдельной колонки
«проверена» нет по той же причине, что нет «сдано» у Задания
(инвариант 12): состояние — это данные, а не флаг рядом с ними.

`file_key` 200 — как у теории (`0005-theory-materials.yaml`), `note` 2000 —
свободный текст, но не сочинение.

### Приём — одна транзакция после укладки всех файлов

```
receive(assignment, problem, receivedOn, verdict, note, files):
  1. existing assignment (владелец)  -> AssignmentNotFoundException
  2. problem ∈ assignment.problems() -> иначе отказ
  3. files не пуст; у каждого тип image или PDF -> иначе отказ
  4. keys = [put(compressed or raw) for each file]   // хранилище
  5. try { create work + file rows } catch { delete(keys); rethrow }
```

Проверки до первого обращения к хранилищу: отказ по типу одного файла
не оставляет в хранилище остальных. Укладка идёт до записи, уборка —
при неудаче записи (standards.md, «Файлы»): второй Работы на паре
не будет благодаря уникальности, и это ровно тот случай, когда запись
падает после укладки — ключи убираются. `addFiles` — тот же порядок
для существующей Работы; позиции продолжают счёт.

Пережатие — как у теории: `FileType.isImage` → `ImageCompression.compress`,
иначе как есть; тип, не подходящий ни под изображение, ни под PDF, —
отказ с текстом «принимаются изображения и PDF». Проверка типа — по тому,
что назвал браузер: содержимое хранилище не разбирает, а пережатие
на не-изображении упадёт само.

`UploadedWorkFile(byte[] content, String contentType)` — своя запись
области, как `UploadedFile` у Задач и `UploadedContent` у теории:
области друг от друга не зависят.

### Удаление — записи, затем файлы

`delete(work)`: строки Работы и файлов уходят в транзакции (файлы —
каскадом), ключи собираются до удаления, и после транзакции
`storage.delete` по каждому. `deleteFile(work, file)`: отказ, если файл
у Работы единственный; иначе строка, затем ключ. Порядок тот же, что
у теории (`TheoryService.delete`, `TheoryService.java:209`): забытый файл
в хранилище никому не мешает, а запись без файла выглядит настоящей.

### Вердикт — `Verdict` с `null` как «не проверена»

```java
public enum Verdict { CORRECT("верно"), INCORRECT("неверно"); }
```

`setVerdict(work, Verdict /* nullable */, String note)` — одно действие
на вердикт и примечание: на экране они в одной форме, и примечание без
вердикта («посмотрю позже») законно. Снять вердикт можно, отправив пустой:
учитель передумал, а «не проверена» — честное состояние. Третьего
значения нет (ADR-0014). Название `Verdict` — в словарь, таблица
перечислений.

### Ответы на вопросы: оба с владельцем из `CurrentUser`

`WorksOfAssignment implements AssignmentWork` →
`assignmentsWithWork(UserId, Collection<AssignmentId>)`: `SELECT DISTINCT
assignment_id … WHERE user_id = ? AND assignment_id IN (…)`. Один запрос
на список — Раздача проверяется целиком. `WorksOfStudent implements
StudentUsage` → `countByStudent(UserId, StudentId)` соединением
с `assignment`, ответ «принято Работ (N)». Оба зависят только
от репозитория и `CurrentUser`, не от `StudentWorkService`: тот зависит
от `AssignmentService`, который собирает `List<AssignmentWork>`, —
зависимость от сервиса дала бы цикл бинов.

Ученик с Работой всегда имеет и Задание, поэтому отказ в удалении
назовёт обе причины — `StudentService.refuseUnlessUnused` собирает
ответы всех ответчиков в один отказ (до этой работы он бросал на первом
ответившем; правка одного метода в `student`, поведение с одним
ответчиком не изменилось).

### Экраны: область `work` владеет экраном С5

- `Addresses.WORKS = "/works"`.
- `GET /works?assignment={id}` — **экран приёма**: `AssignmentService.assignment(id)`
  (Ученик, «не сдано»), `problemsOf` (состав, `FoundProblem`),
  `StudentWorkService.ofAssignment(id)` → `Map<ProblemId, StudentWork>`.
  По каждой Задаче состава: Работа — дата получения, «не проверена»
  или вердикт, примечание, файлы ссылками (`temporaryLink` по каждому,
  считается при показе), формы «добавить файлы», «вердикт и примечание»,
  «удалить файл» у каждого, «удалить Работу»; без Работы — форма приёма:
  `<input type="file" name="files" multiple accept="image/*,application/pdf">`,
  дата получения (`type="date"`, по умолчанию сегодня), вердикт
  радиокнопками с «не проверять сейчас», примечание.
- `GET /works?student={id}` — **Работы Ученика**: `StudentService.student`,
  `ofStudent(id)` — Работы с датой, вердиктом, номером Задачи и ссылкой
  на экран приёма Задания, новые первыми. Без параметров — на `/assignments`.
- `POST /works` — приём (multipart); `POST /works/{id}/files` — добавить;
  `POST /works/{id}/files/{fileId}/deletion`; `POST /works/{id}/verdict`;
  `POST /works/{id}/deletion`. После каждого — редирект на экран приёма
  Задания; отказ (`IllegalArgumentException`) — экран приёма с текстом.
- Страница Задания `assignment/assignment.html` — ссылка «Работы»
  на `/works?assignment={id}`; карточка Ученика — «Работы Ученика»
  на `/works?student={id}`. Только адреса в шаблонах: `assignment`
  и `student` о `work` в коде не узнают.

Экран приёма и список — под телефон: `<meta name="viewport"
content="width=device-width, initial-scale=1">`, поля формы на всю
ширину, без таблиц и фиксированных ширин. Ссылка на файл открывается
в новой вкладке — ссылка временная, и страница за ней должна остаться.

### Пределы загрузки

`spring.servlet.multipart.max-file-size: 20MB`, `max-request-size: 100MB`
в `application.yaml` с комментарием: снимок с телефона — до 10 МБ, приём —
несколько снимков; пережатие идёт после приёма, а не вместо него.
Превышение Spring отклоняет до контроллера — `MaxUploadSizeExceededException`;
показывать его текстом на экране приёма — обработчик в контроллере
`work`, как отказы сервиса.

### Тесты формы и изоляции

`OwnerIsRequiredByWorksTest` по образцу `OwnerIsRequiredByStudentsTest`
(без списка исключений: их нет); таблицы `student_work`,
`student_work_file` несут `user_id`. `WorksAreFilteredByOwnerTest` — HTTP
двумя Учителями: экран приёма чужого Задания и Работы чужого Ученика —
404; приём по чужому Заданию — 404, Работ нет; вердикт, файлы и удаление
чужой Работы — 404, данные А прежние. `WorkIsOnePerPairTest` — вставка
второй Работы на паре и Работы по Задаче не из состава не проходит
в репозитории (нарушение ключа), в сервисе — отказ с текстом.
`AssignmentWorkAnsweredTest` — «не сдано» и удаление Задания с Работой
(включая Раздачу с одним удержанным Заданием); после удаления Работы —
обратно. `WorkFilesTest` — пережатие снимка, PDF байт в байт, ссылка без
подписи и после удаления не отдаёт, тип отклоняется до укладки (в хранилище
ничего не появилось). `WorkScreenTest` — экран приёма, приём двух файлов
через `postMultipart` с несколькими файлами в поле, вердикт позже, список
Работ Ученика, `viewport` в разметке.

`Browser.postMultipart` получает перегрузку с `List<FilePart(field,
filename, contentType, content)>`; прежняя остаётся и зовёт новую.

## Risks / Trade-offs

**Ключ на `assignment_problem` держит Работу за состав Задания** →
это и нужно: состав после выдачи не меняется (ADR-0037), а Задание
с Работой не удаляется; ключ — второй рубеж за сервисом.

**Пределы 20/100 МБ — память при приёме** → файлы читаются в `byte[]`
(так у Задач и теории); пять снимков по 10 МБ — 50 МБ на запрос, один
Учитель, один сервер; при росте потока — стриминг, но не сейчас.

**Тип файла — по слову браузера** → подделанный тип с не-изображением
внутри уронит пережатие явной ошибкой, а PDF с чужим содержимым просто
не откроется; хранилище о содержимом не судит по замыслу.

**Ссылка на файл живёт 10 минут** (`locus.file.link-ttl`) → экран приёма
считает ссылки при показе; учитель, открывший страницу утром и нажавший
вечером, получит отказ и обновит страницу. Это свойство хранилища,
не Работ.

**Экран приёма читает по вызову `temporaryLink` на файл** → подпись
считается локально без сети (ADR-0021), десятки файлов — миллисекунды.

**Работа удаляется свободно** → решение ADR-0038; отказ владельцу
на гейте — повод для другой записи, не для флага.

**Непроверенные Работы никто не напомнит** → ADR-0017; экран приёма
и список Работ показывают «не проверена» явно.

## Migration Plan

Одна миграция `0008-submission-review.yaml`, два changeset'а:
`student_work`, затем `student_work_file`. Данных к переносу нет,
обратной совместимости не требуется (ADR-0024). `application.yaml` —
пределы загрузки; `compose.yaml` не трогается.
