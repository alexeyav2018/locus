# Design

## Context

Мотив — proposal.md, «Why». Нынешнее устройство:

- `ProblemFilter` (`src/main/java/ru/locus/problem/ProblemFilter.java:43-48`)
  — условия разметки: узел, Методы с режимом, Характеристики с режимом,
  Часть; пустое условие снимается при сборке.
- `ProblemSearchController.search` (`ProblemSearchController.java:84-109`)
  — форма `GET /problems`, условия в адресе; отказ сервиса
  (`IllegalArgumentException`) показывается строкой `error` вместо
  результата; модель — `filter`, `found`, `foundCount`, `textlessCount`.
- `ProblemService.search` (`ProblemService.java:143-150`) разворачивает
  узел в поддерево и зовёт `ProblemRepository.search`; имена разметки —
  `named`. Рядом `ProblemService.problems(ids)` (`:110-118`) читает
  Задачи по номерам для Заданий и Разминок: порядок запроса, отсутствующий
  номер — отказ.
- `ProblemRepository`: `findByTopic` (`:126-138`), `findByIds`
  (`:150-165`), `search` (`:202-238`) — все `order by p.id`.
- `ProblemTools.findProblems` (`ProblemTools.java:61-96`) — тот же
  `ProblemFilter`, ответ — JSON-массив Задач.
- `templates/problem/search.html` — одна форма `.filters card sticky`
  в левой колонке `.split`, результаты справа.

## Goals / Non-Goals

**Goals:**

- Список номеров с бумаги — один ввод, один результат, без листания.
- Режим поиска (номера или разметка) виден по странице, а не по подсказке.
- Опечатка в номере не прячет остальные Задачи.

**Non-Goals:**

- Диапазонов «3-7» нет (ADR-0064, отвергнутое).
- Подбор под пробел (`mastery-views`) номеров не передаёт.
- Номера не пишутся в Задание или Разминку напрямую: найденное
  по-прежнему отмечается галочками и уходит в «Выдать ДЗ» / «Провести
  Разминку».

## Decisions

### Данные: общая библиотека, фильтра по владельцу нет

Поиск по номерам читает только Задачи общей библиотеки; читают все
вошедшие, менять нечего. `ProblemRepository` параметра владельца
не принимает, новых методов изменение не добавляет — используется
существующий `findByIds`. `SearchIsNotFilteredByOwnerTest` в силе.

### Разбор поля — значение `ProblemNumbers`

Новый тип `ProblemNumbers` в `ru.locus.problem`: `parse(String text)`
делит текст по `[\s,;]+`, каждый кусок — только цифры, иначе
`IllegalArgumentException` «Не разобрано: «пять»» (все неразобранные
куски через запятую, в порядке ввода); число, не влезающее в `long`, —
такой же кусок. Повтор снимается, порядок ввода значения не имеет.
Пустой после разбора — отказ «Не задано ни одного номера». Второй
конструктор `of(List<Long>)` — для инструмента, с теми же правилами
повтора и пустоты.

Почему тип, а не разбор в контроллере: правило одно на страницу
и на Помощника (ADR-0064), а контроллер и инструмент — два клиента
сервиса; разбор в каждом разошёлся бы молча. Почему не в `ProblemFilter`:
номера отменяют фильтр, а не дополняют его — запись с полем, при котором
остальные поля ничего не значат, читалась бы неверно.

### Отбор по номерам — `ProblemService.byNumbers`

`byNumbers(ProblemNumbers)` → запись `NumberedProblems(List<FoundProblem>
found, List<ProblemId> missing)`: `findByIds` одним запросом, `named`
для найденных, ненайденные — по убыванию номера, как и найденные, чтобы строка «Нет в библиотеке» читалась в том же
порядке, что список. Отказа на ненайденном нет — в этом отличие
от `problems(ids)`, которым Задания проверяют состав перед выдачей,
и смешивать их нельзя. Без `@PreAuthorize`, как всё чтение библиотеки.

### Порядок — `order by p.id desc` в трёх запросах

`findByTopic`, `findByIds`, `search`. `problems(ids)` от порядка
`findByIds` не зависит — переставляет по запросу. `findByTopic` зовёт
ещё перестройка дерева (`ProblemService.java:624`) — только как
множество. Порядок в отображении и в инструменте следует сам.

### Контроллер: номера — отдельная ветка

`@RequestParam(required = false) String numbers`. Параметр есть (даже
пустой) — ветка номеров: `ProblemNumbers.parse`, `byNumbers`; модель
`filter` = `ProblemFilter.empty()` (форма разметки показывается пустой),
`numbers` — введённый текст, `missing` — ненайденные. Параметра нет —
прежняя ветка разметки, `numbers` в модели пустой. Отказ разбора — тот же
`error`, что у несуществующего узла.

Почему пустое поле — отказ, а не вся библиотека: учитель нажал «Поиск»
у номеров и увидел бы всю библиотеку как ответ на «ни одного номера» —
правдоподобный результат не на тот вопрос.

### Экран: две формы в левой колонке

Левая колонка — `<div class="sticky">` с двумя карточками: форма
«Номера Задач» (`<textarea name="numbers" rows="2">`, кнопка «Поиск»,
скрытый `from`) и прежняя форма разметки. Строка «Нет в библиотеке: 4,
99» — над «Найдено Задач», класс `alert`: это потеря, которую учитель
должен заметить. Если не найдено ничего, остаются и «Нет в библиотеке»,
и «По этим условиям Задач нет.» — формулировка общая и для номеров
верна. «Сбросить» в форме разметки ведёт на `/problems` без параметров
и сбрасывает обе.

### Инструмент: `numbers` и ответ объектом

`numbers` — массив целых (как `methods`), а не строка: у инструмента
разбор текста не нужен, и тип схемы сам отклоняет постороннее. Есть
`numbers` (даже пустой) — отбор по номерам, прочие аргументы
не действуют; пустой массив — отказ, как пустое поле.

Ответ всегда объект `{"problems": [...], "missing": [...]}`; без
`numbers` `missing` пуст. Альтернатива — массив без номеров и объект
с ними — отвергнута: форма ответа, зависящая от аргумента, заставляет
читателя ветвиться, а прежний массив никем, кроме тестов, не разбирается
(правило в `agent/CLAUDE.md` о форме ответа не говорит). Описание
инструмента называет оба способа и что номера отменяют условия.

## Risks / Trade-offs

- **Смена формы ответа `find_problems`.** Помощник, заученно читающий
  массив, не встретится: процесс на Реплику, описание инструмента
  читается заново каждый раз (ADR-0054).
- **Порядок по убыванию везде** — привычка к возрастанию сломается
  у учителя один раз; решение владельца.
- **Тесты, опиравшиеся на возрастание** (`containsExactly` по номерам),
  упадут — перечислены в tasks.md, правятся в том же разделе.

## Migration Plan

Схема не меняется; обновление обычное, с остановкой (ADR-0024).
