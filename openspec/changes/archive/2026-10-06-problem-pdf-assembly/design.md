# Design

## Context

Сегодня у Задачи два слота файла, и каждый принимает только готовый PDF:
форма `problem/form.html` шлёт поля `condition` и `solution`,
`ProblemController.create` превращает их в `UploadedFile`
(`ProblemController.java:216`), `ProblemService.create` проверяет наличие
и кладёт оба в `FileStorage` (`ProblemService.java:256`). Замена — отдельные
формы `POST /problems/{id}/condition|solution` и `replaceCondition`/
`replaceSolution` с проверкой заморозки (`refuseUnlessUnused`).

У `FileStorage` три операции и сознательно нет чтения по ключу
(`FileStorage.java:7`). Пределы загрузки — одна настройка контейнера
на всё приложение: 20 МБ на файл, 100 МБ на запрос
(`application.yaml:25`), превышение ловит только экран приёма Работ
(`StudentWorkController.tooLarge`). JavaScript в шаблонах проекта пока нет
ни строчки; ADR-0020 предусматривает точечные вставки.

Граница общего и личного. Результат — PDF Задачи, общая библиотека: ведёт
Администратор, по владельцу не фильтруется, как и прежде. Новые данные —
черновик сборки: временный, принадлежит загрузившему, фильтруется по
владельцу на каждом запросе; без владельца — только две уборки (ADR-0044).

## Goals / Non-Goals

**Goals:**
- Собрать PDF слота из картинок и диапазонов целых страниц PDF на сервере.
- Результат без ресурсов не взятых страниц.
- Черновик сборки: собственность загрузившего, жизнь до сборки, попутная
  уборка.
- Предел загрузки инструмента выше общего, общий — прежний для остальных.

**Non-Goals:**
- Обрезка страницы до области задачи — следующий элемент
  `problem-pdf-crop`.
- Хранение сборника для повторной нарезки (сущность «Источник») — отвергнуто
  в ADR-0044.
- Предпросмотр страниц сборника в браузере: Администратор указывает номера
  страниц, сверяясь со своей копией; проверяет результат по ссылке Задачи.
- HEIC — элемент `heic-images`.
- Сохранение подписи и разметки формы заведения при отказе — сегодня форма
  их теряет (`ProblemController.create`, ветка отказа), и это прежнее
  поведение, не этого изменения. Сохраняется только порядок сборки:
  без него пришлось бы заново загружать сборник.

## Decisions

### Сборка — чистая функция над страницами на PDFBox 3

`PdfAssembly` получает упорядоченный список кусков «картинка» или «PDF
и диапазон» и возвращает байты PDF. Ни базы, ни хранилища, ни прав — только
PDFBox; поэтому самое хрупкое проверяется модульными тестами без контекста
Spring. Выбор сервера и PDFBox — решение владельца в карточке и ADR-0044.

### Страница переносится белым списком ключей и с вычищенными ресурсами

Обычный перенос страницы (`importPage`, `Splitter`) копирует словарь
страницы как есть, и при записи результата PDFBox сохраняет всё, что из него
достижимо. Отсюда три утечки, каждую закрывает отдельный приём:

- **Общий словарь ресурсов.** Генераторы сборников часто дают всем страницам
  один `/Resources` со всеми картинками и шрифтами книги. Для каждой
  взятой страницы строится **новый** словарь ресурсов: в него попадают только
  те записи, чьи имена встречаются среди операндов её потока содержимого
  (разбор `PDFStreamParser` по лексемам, включая параметры встроенных
  картинок). Сравнение по имени без учёта категории может взять лишнюю
  запись при совпадении имён в разных категориях — это лишний килобайт,
  а не потерянный глиф, и выбрано осознанно: разбор по операторам
  (`Do`, `Tf`, `gs`, `cs`, `scn`, `sh`, `BDC`) был бы точнее и хрупче.
  Общий словарь при этом **не правится на месте** — его делят другие
  страницы.
- **Вложенные формы и узоры со своими ресурсами.** Form XObject и мозаичный
  узор (`PatternType 1`) несут свой `/Resources`, который генератор тоже
  может сделать общим. Их ресурсы вычищаются тем же правилом рекурсивно, по
  их собственному потоку; правка на месте здесь допустима — результат зависит
  только от потока самого объекта, а исходник после сборки выбрасывается.
  Форма без своего `/Resources` пользуется ресурсами страницы — её имена
  добавляются к именам страницы. Шрифты Type3 переносятся целиком: случай
  редкий, а вычистка `CharProcs` дороже пользы.
- **Ссылки на другие страницы.** `/Annots` (ссылки, комментарии), `/Parent`,
  `/B` (статьи), `/StructParents` указывают на соседние страницы и дерево
  документа. Новая страница строится **белым списком**: `MediaBox`,
  `CropBox`, `Rotate`, `UserUnit`, `Contents`, вычищенные `Resources` —
  с учётом наследования от дерева страниц. Пометки не переносятся
  (ADR-0044, «Последствия»).

Альтернатива — отрисовать страницу картинкой — отвергнута: теряется
векторная чёткость формул и растёт объём.

### Картинка — одна страница, байты не пережимаются

JPEG вкладывается как есть (`JPEGFactory.createFromByteArray`, без
перекодирования), PNG — без потерь (`LosslessFactory`). Страница размером
с картинку из расчёта **1 пиксель = 1 пункт**: подгонки под лист нет
по карточке, а сведения о разрешении в снимках с телефона ненадёжны
и сделали бы размер страницы случайным. Просмотрщик всё равно вписывает
страницу в окно, печать — в лист.

Ориентация по EXIF: JPEG не перекодируется, поэтому разворот делается
матрицей размещения картинки на странице, а у страницы стороны меняются
местами для поворотов на 90°. Ориентацию читает `ExifUtils` из
Thumbnailator — та же библиотека уже разворачивает сканы Работ
(`ImageCompression`), второй не заводится.

### Черновик — строка в базе и файл в рабочей папке, не в `FileStorage`

Таблица `assembly_draft`: идентификатор, `owner_user_id`, имя исходного
файла, вид (`IMAGE`/`PDF`), тип содержимого, число страниц, имя файла
в рабочей папке, время загрузки. Содержимое — файл в
`locus.problem.draft.directory`, имя — случайный UUID, а не идентификатор
(по той же причине, что ключ хранилища, `FileKey.java:7`).

Почему не `FileStorage`: ему пришлось бы добавить чтение (ADR-0021,
ADR-0044). Почему не только память процесса: владелец и срок — данные,
которые удобнее и проверяемее держать там же, где у остальных записей,
с тем же `UserId` в сигнатурах; уборка при старте всё равно делает
состояние после перезапуска пустым.

Загрузка пишет поток прямо в папку (`MultipartFile.transferTo`), не держа
сборник в памяти целиком; PDF открывается с диска (`Loader.loadPDF(File)`)
и при загрузке — чтобы счесть страницы и отклонить неразбираемое
или закрытое паролем сразу, а не при сборке.

### Репозиторий черновиков: `UserId` всюду, кроме двух уборок

`AssemblyDraftRepository`: `create(UserId, …)`, `findByIds(UserId, ids)`,
`deleteByIds(UserId, ids)` и две уборки без владельца —
`deleteCreatedBefore(Instant)` и `deleteAll()`, обе возвращают только
имена файлов для удаления с диска, ничего о черновиках не показывая.
Исключения перечислены поимённо в `OwnerIsRequiredByDraftsTest` по образцу
`OwnerIsRequiredByAssignmentsTest`; изоляция — `DraftsAreFilteredByOwnerTest`.
Чужой черновик неотличим от несуществующего: `findByIds` его просто
не возвращает, и сервис отвечает одним отказом «черновика нет».

### Слот принимает «готовый файл или порядок сборки»

В `ProblemService` у `create`, `replaceCondition`, `replaceSolution` тип
файла слота меняется с `UploadedFile` на `ProblemPdf` — запечатанный
интерфейс с двумя вариантами: `UploadedFile` (готовый) и `PdfAssemblyOrder`
(список строк «черновик, с, по»). Разрешает его `ProblemService` через
`AssemblyDraftService.assemble` **после** проверок разметки и заморозки,
до укладки в хранилище; после сохранения Задачи зовёт
`AssemblyDraftService.discard` для всех черновиков обоих слотов.

Почему в сервисе, а не в контроллере: «удалить черновики только если
Задача сохранилась» — правило предмета, и при обращении в обход формы
оно должно срабатывать так же (standards.md, «Слои и границы»);
`ProblemControllerIsThinTest` продолжает запрещать контроллеру
репозитории и хранилище.

Удаление черновиков в транзакции Задачи: строки удаляются в ней же,
файлы с диска — после фиксации (`TransactionSynchronization.afterCommit`).
Откат Задачи оставляет и строки, и файлы — форма показывает тот же порядок
сборки.

Готовый файл и порядок сборки на одном слоте одновременно — отказ
в контроллере при разборе запроса («выберите один способ»): это разбор
формы, а не правило Задачи — сервис получает ровно один вариант по типу.

### Форма: строки сборки рисует сервер, JavaScript только грузит и двигает

Первая в проекте вставка JavaScript (ADR-0020 её предусматривает), и она
держится минимальной:

- у слота — поле выбора исходника; выбор файла отправляет его
  `fetch`-запросом на `POST /problems/drafts`; ответ — **фрагмент Thymeleaf**
  со строкой сборки (имя, число страниц, поля «с»/«по», кнопки «выше»,
  «ниже», «ещё диапазон», «убрать»), который скрипт вставляет в список
  слота;
- порядок строк — порядок в документе: поля `conditionDraft`,
  `conditionFrom`, `conditionTo` (и `solution…`) повторяются в каждой строке,
  и у картинки «с»/«по» — скрытые единицы, чтобы списки не разъехались;
- при отказе формы контроллер перерисовывает строки тем же фрагментом
  из присланных списков (`AssemblyDraftService.rows`), так что разметка
  строки одна.

Альтернатива без JavaScript — отправлять всю форму ради каждой загрузки
и перерисовывать её — отвергнута: форма заведения при перерисовке сегодня
теряет поля, и каждая загрузка исходника стирала бы набранную разметку.

**Уточнено при слиянии с develop (06.10.2026).** Пока изменение шло,
в `develop` пришёл новый интерфейс с
[ADR-0041](../../../context/adr/0041-edinaya-sistema-oformleniya.md):
весь JavaScript — в одном `static/js/locus.js`, встроенных скриптов
и `<style>` в шаблонах нет. Скрипт сборки переехал из конца
`problem/form.html` в `locus.js` разделом 5, стили строк — в `locus.css`;
адрес загрузки поле исходника несёт атрибутом `data-assembly-url`. Поведение
не изменилось. Сама запись о сборке перенумерована в ADR-0044: номера
0041–0043 в `develop` заняты.

### Уборка: срок при открытии инструмента, всё при старте

«Открытие инструмента» — показ формы заведения и правки Задачи
и загрузка черновика: каждый вызывает `AssemblyDraftService.sweep()`,
удаляющий черновики **всех** Пользователей старше
`locus.problem.draft.ttl` (по умолчанию 24 часа) от бина `Clock`. При
старте — `ApplicationRunner` удаляет все строки и всё содержимое рабочей
папки, включая файлы без строки.

Почему срок, а не «все черновики пользователя при открытии»: вторая
вкладка с той же формой молча лишилась бы своих черновиков. Срок с запасом
длиннее сессии входа: незавершённая форма не переживает её истечения,
поэтому черновик старше суток гарантированно брошен.

### Предел загрузки: контейнер — по инструменту, общий — перехватчиком

Настройка контейнера `spring.servlet.multipart` поднимается до предела
инструмента: 100 МБ на файл, 110 МБ на запрос. Общий предел (20 МБ на файл,
100 МБ на запрос) переезжает в `locus.upload.*` и проверяется
`UploadLimitInterceptor` на всех обработчиках, кроме загрузки черновика;
превышение он сообщает тем же `MaxUploadSizeExceededException`, так что
экран приёма Работ продолжает показывать отказ своим текстом без правки.
Исключение отмечается аннотацией на методе (`@LargeUpload`), а не списком
адресов: адрес переименуют, а аннотация переедет вместе с методом.

Альтернатива — второй сервлет со своей настройкой multipart для адреса
черновиков — отвергнута: второй контекст ради одного адреса, и общий
предел всё равно стоял бы в двух местах.

## Risks / Trade-offs

- [Генератор кладёт ресурсы так, что вычистка по именам что-то упускает —
  страница результата без глифа] → тест на сборнике с разными шрифтами
  и формами; при появлении такого PDF в практике — заметно сразу
  при просмотре собранной Задачи, Администратор приложит готовый PDF.
- [Сборник в 100 МБ держит память при сборке] → PDF читается с диска
  и подгружает объекты лениво; результат — несколько страниц.
- [Рабочая папка на диске VPS] → чистится при старте и по сроку; объём
  ограничен пределом инструмента на файл.
- [Первый JavaScript без тестов на JavaScript] → в скрипте нет правил:
  только загрузка и перестановка узлов; всё проверяемое — на сервере,
  а сервер принимает те же поля и без скрипта.
