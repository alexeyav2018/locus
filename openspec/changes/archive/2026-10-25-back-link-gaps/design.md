# Design

## Context

Возврат параметром `from` ([ADR-0042](../../context/adr/0042-vtorichnoe-po-knopke-i-vozvrat.md))
устроен так: ссылка вглубь несёт `from=${shell.here}`, `ShellAdvice` кладёт
проверенный `ReturnTo.safe` адрес в `shell.back`, страница рисует
«← …» по `shell.backOr(...)`. На POST `ShellAdvice` читает `from` из
параметров действия, поэтому отказ, показанный тем же запросом, «назад»
не теряет — если форма отправила `from`.

Что видно в коде сегодня:

- `dictionary/dictionaries.html:26`, `taxonomy/tree.html:12` — заголовок
  без строки «← …». Ссылки выбора (`/dictionaries?method=`,
  `taxonomy/branches.html:37` `/taxonomy?node=`) и формы `from` не несут;
  `DictionaryController` (`:99`, `:128`, `:175`, `:179`)
  и `TaxonomyController` (`:153`, `:178`, `:250` — `atNode`) переадресуют
  без него.
- `problem/search.html` (сюда ведёт «Подобрать задачи»
  `mastery/student.html:40` с `from`) и `assignment/list.html` (сюда ведёт
  `student/student.html:41` с `from`) — то же: `from` приходит, но не
  показывается, а форма отбора (GET) его теряет.
- `ProblemDraftController.java:109` — «Сохранить черновик» переадресует
  на `/problems/intake/{id}` без `from`; `:175` — удаление ведёт в список
  без `from`; `:198` — утверждение ведёт на `/problems/{id}` без `from`.
- Форма Задачи и страница Встречи уже несут `from` через действия
  (`problem/form.html:49`, `ScheduleController.java:199-201`) — образец.

## Goals / Non-Goals

**Goals:**
- Словари, рубрикатор, поиск Задач и список Заданий, открытые с `from`,
  показывают «← Назад» и сохраняют `from` через свои действия.
- Черновик Задачи сохраняет `from` после записи и отказа; утверждение
  и удаление ведут в список черновиков с `from`, а без оставшихся
  черновиков — по возврату списка.

**Non-Goals:**
- Новые ссылки с `from` туда, где их нет (например, «Искать
  по библиотеке» с дерева): правило ADR-0060 о них есть, но пробела
  в сеансе там не было.
- Ссылка «завести Тему в рубрикаторе» со страницы черновика — это
  `intake-tabs`.
- Переход после заведения Задачи формой Задачи (`ProblemController`) —
  прежний.

## Decisions

### Р1. Две функции в `ReturnTo`: дописать `from` и выдать `from` для переадресации

`ReturnTo.carried(address, from)` — адрес действия с дописанным
`from`, если тот проходит `safe`; якорь (`#node-5`) остаётся последним.
Значение кодируется как параметр запроса (как в
`AnswerMarkdown.java:74`). Иначе — адрес как есть.

`ReturnTo.location(safe)` — проверенный адрес для `redirect:`: символы,
недопустимые в адресе (не-ASCII, пробел, `{`, `}`, `"`, `<`, `>` и т. п.),
кодируются в UTF-8 `%XX`, уже закодированное (`%2F`) не трогается. Иначе
кириллица из условия поиска ушла бы в заголовок `Location` сырой,
а `{…}` Spring принял бы за переменную шаблона адреса.

*Отвергнуто:* `UriComponentsBuilder.fromUriString(from).encode()` —
кодирует и `%`, ломая вложенный `from`; повторять это в каждом
контроллере — расползание. `ScheduleController` переписывать на общую
функцию не будем: его код уже верен, а правка ради единообразия
в чужой области — вне карточки.

### Р2. POST-формы несут `from` в адресе действия, GET-формы — скрытым полем

Как `problem/form.html:49`: `th:action="@{/taxonomy(from=${shell.back})}"`.
`ShellAdvice` читает `from` и из адреса, и из тела. У GET-формы браузер
отбрасывает запрос адреса действия, поэтому там — скрытое поле
`<input type="hidden" name="from" th:if="${shell.back}" …>`; без
`from` поля нет, и адрес отбора прежний.

Ссылки страницы на саму себя (выбор записи, узла, «Сбросить») несут
`from=${shell.back}`. Если `back` пуст, Thymeleaf параметр выводит
без значения либо не выводит — оба случая `ReturnTo.safe` отбрасывает;
проверить на тесте, при лишнем `?from` — выводить условно.

*Проверено при реализации (раздел 2):* Thymeleaf 3.1 параметр
со значением `null` выводит именем без значения — `?method=5&from`.
Вместо условных выражений у каждой ссылки `Shell` получил
`carried(address)` — тот же `ReturnTo.carried` с возвратом страницы:
`th:href="@{${shell.carried('/dictionaries?method=' + id)}}"`. Без
возврата адрес остаётся прежним, с ним — несёт `from`. Так написаны
ссылки выбора и формы словарей и дерева; формы, уже несущие
`from=${shell.back}` (Задача, вычитка), не переписываются — их
лишний пустой `from` невидим и отбрасывается `safe`.

### Р3. Контроллеры словарей и дерева принимают `from` и передают его в переадресацию

Каждый POST-обработчик получает `@RequestParam(required = false) String from`
и возвращает `"redirect:" + ReturnTo.carried(адрес, from)`. В дереве
это `atNode(id, from)` и ветка «к корню» для удаления и распределения.
Отказ показывается тем же запросом — `shell.back` берётся из `from`
действия, контроллеру делать ничего не нужно.

Тесты тонкого контроллера (`*ControllerIsThinTest`) не меняются:
репозиториев у контроллеров не прибавляется.

### Р4. Утверждение и удаление черновика — в список черновиков с `from` черновика; список не вкладывается сам в себя

Страница черновика открывается из двух мест: из списка черновиков
(`from` = адрес списка, у которого свой `from` — Разговор) и из ответа
Помощника (`from` = Разговор). Куда вести после утверждения:

1. Черновиков у учителя не осталось (`ProblemDraftService.count() == 0`) —
   **по возврату списка**: если `from` — сам список, то `from` списка;
   иначе `from`; не прошёл `safe` — `/assistant`, раздел по умолчанию
   ссылки «назад» списка (`intake-list.html:16`). Переадресация — через
   `ReturnTo.location` (Р1).
2. Иначе, если `from` — сам список (путь `from` равен
   `Addresses.PROBLEM_INTAKE`), — на этот адрес с параметром
   `created=<id Задачи>` (прежний `created` заменяется): список
   с тем же возвратом, без вложения списка в список.
3. Иначе — `/problems/intake?from=<from>&created=<id>`.

Удаление ведёт так же, но без `created`. Это сверх карточки: карточка
говорит только об утверждении, но «Удалить черновик» — тот же уход
со страницы черновика к оставшимся, и прежний переход в список
без `from` терял бы Разговор так же.

*Уточнено при реализации (раздел 4):* в п. 2 список не берётся адресом
`from` с заменой `created`, а строится заново — `/problems/intake?created=<id>`
с возвратом списка (`from` из `from`), — так же, как в п. 3. У списка
других параметров нет, поэтому это тот же адрес, и п. 2 и 3 сходятся
в одну ветку: «возврат списка» вычисляется один раз и служит и
переадресацией (п. 1), и `from` нового списка. Номер в `created` —
`Long`: не-число отвечает 400, как любой параметр-число в Локусе;
«набран руками» в Р5 — несуществующий номер, он надписи не даёт.

*Отвергнуто:* всегда вести на `/problems/intake?from=<from>`, вкладывая
список в список, — ссылка «назад» списка вела бы снова на список,
и до Разговора пришлось бы нажимать дважды.

### Р5. Надпись «Заведена Задача № N» — по параметру `created`, а не через сеанс

Список читает `created`, достаёт Задачу `ProblemService.problem` и кладёт
в модель; надпись — ссылка на `/problems/{id}` с `from=${shell.here}`.
Задачи с таким ключом нет (параметр набран руками, Задачу удалили) —
надписи нет, отказа нет: это подсказка, а не данные.

*Отвергнуто:* flash-атрибуты Spring — состояние в сеансе, которое
ADR-0042 уже отклонил для возврата, и в проекте их нет нигде. Параметр
переживает перезагрузку — надпись при этом остаётся, что безвредно.

Задача общая (библиотека), видна любому вошедшему: подставленный
чужой номер ничего не раскрывает сверх поиска.

### Р6. Запись черновика переадресует на него же с `from`

`write` возвращает `redirect:` + `ReturnTo.carried("/problems/intake/{id}", from)`.
Форма вычитки уже шлёт `from=${shell.back}` в адресе действия
(`intake.html:109`, `:159`, `:161`); форма удаления — проверить и
дописать. Отказы показываются тем же запросом и `from` уже держат.

### Р7. Поиск и список Заданий показывают «← Назад» только с `from`

Это разделы шапки: без `from` строки «назад» на них нет, как и прежде;
с `from` — `← Назад` по `shell.back`. Своё название (как «← К Ученику»)
не подобрать: приходят сюда с разных страниц.

### Р8. `ux-concept.md`, раздел 11, — через этот цикл

Раздел 11 «Контекст живёт до действия, не через него» и правило 8
для новых экранов противоречат ADR-0060. Правится смысл, поэтому —
пунктом этого изменения: раздел 11 говорит, что `from` переживает
действие, а переход прямо по `from` — только без следующей страницы;
правило 8 дополняется формами и ссылками на себя.

### Р9. Период срока в сводке Заданий — `dueFrom` и `dueTo`, а не `from` и `to`

*Найдено при реализации (раздел 3):* сводка `/assignments` называла
начало периода срока параметром `from` — тем же именем, что и возврат
ADR-0042. Плитка «Задания Ученика» (`student/student.html:41`) шлёт
`from=/students/5`, Spring пытается прочесть его датой, и страница
отвечает 400: переход с карточки Ученика был сломан ещё до этой работы.

Варианты: переименовать возврат на этой странице (ломает единое имя
и `ShellAdvice`, который читает только `from`) или переименовать даты
периода. Выбраны даты: `dueFrom` и `dueTo` — пара переименована
целиком, чтобы не читалось «от» без «до». Сохранённые закладки
с `from=<дата>` теряют начало периода — `ReturnTo.safe` такой `from`
отбрасывает, страница открывается без отбора по нему, отказа нет.
Спека `assignments` имён параметров не называет, дельты нет.

## Risks / Trade-offs

- **Рост вложенных `from`.** Адрес дерева с `from` становится `from`
  его Задач; цепочка обрывается пределом `ReturnTo.MAX_LENGTH` (1000) —
  слишком длинный возврат отбрасывается, «назад» ведёт на раздел
  по умолчанию. Принято ADR-0060, последствия.
- **Переход прямо по `from`.** Адрес только внутренний (`ReturnTo.safe`),
  тот же, что уже стоит ссылкой «назад», — наружу не уводит.
- **Раздел по умолчанию списка записан дважды** — в шаблоне
  (`backOr('/assistant')`) и в контроллере (`Addresses.ASSISTANT`).
  Расхождение сторожит тест «последний черновик без `from` ведёт
  на `/assistant`».

Схема и данные не меняются; обновление — обычная выкладка.
