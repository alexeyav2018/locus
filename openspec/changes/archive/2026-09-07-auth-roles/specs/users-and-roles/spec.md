## Purpose

Кто работает в системе и что ему позволено. Описывает учётные записи, вход,
роли Администратора и Учителя как наборы прав, а также распоряжение учётными
записями: заведение, роли и пароли. Прикладного смысла для учителя здесь нет —
это условие, при котором у остального появляется владелец.

## ADDED Requirements

### Requirement: Работа возможна только после входа

Система SHALL требовать входа для любой страницы и любого действия, кроме
формы входа и её отправки. Обращение неаутентифицированного посетителя
к прочим адресам MUST приводить к форме входа, а не к запрошенной странице.

Правило распространяется на все адреса, включая те, что не показаны ни в одном
меню: доступность страницы определяется правами, а не тем, есть ли на неё
ссылка.

#### Scenario: Обращение к странице без входа

- **WHEN** посетитель, не выполнивший вход, запрашивает любую страницу системы
- **THEN** он получает форму входа
- **AND** содержимое запрошенной страницы ему не показывается

#### Scenario: Обращение к адресу, на который нет ссылки

- **WHEN** посетитель, не выполнивший вход, запрашивает адрес напрямую, минуя
  переходы по ссылкам
- **THEN** он получает форму входа

### Requirement: Вход по имени входа и паролю

Система SHALL пускать пользователя по паре «имя входа и пароль». Имя входа —
произвольная строка, уникальная в системе; адресом почты оно не является
и почтой не проверяется.

При неверной паре система MUST отказывать во входе, не сообщая, что именно
неверно — имя или пароль. Пароль MUST храниться так, чтобы его нельзя было
восстановить из хранилища.

#### Scenario: Верные имя входа и пароль

- **WHEN** пользователь отправляет форму входа с верной парой
- **THEN** сеанс начат
- **AND** пользователь попадает на главную страницу системы

#### Scenario: Неверный пароль

- **WHEN** пользователь отправляет форму входа с существующим именем входа
  и неверным паролем
- **THEN** во входе отказано
- **AND** сообщение об отказе не позволяет отличить неверный пароль от
  несуществующего имени входа

#### Scenario: Несуществующее имя входа

- **WHEN** пользователь отправляет форму входа с именем, которого в системе нет
- **THEN** во входе отказано
- **AND** сообщение об отказе такое же, как при неверном пароле

### Requirement: Завершение сеанса

Система SHALL позволять вошедшему завершить сеанс. После завершения доступ
к страницам системы MUST требовать нового входа.

#### Scenario: Выход

- **WHEN** вошедший пользователь выполняет выход
- **THEN** сеанс завершён
- **AND** следующее обращение к любой странице системы приводит к форме входа

### Requirement: Права определяются набором ролей, активная роль не выбирается

У пользователя SHALL быть произвольный набор ролей: Администратор, Учитель,
обе сразу или ни одной. Вошедший MUST получать объединённый функционал всех
своих ролей; выбирать активную роль ни при входе, ни в работе не требуется.

Роль Администратора даёт распоряжаться общим — библиотекой и учётными
записями. Роль Учителя даёт вести своё — учеников и всё, что о них накоплено.
Пользователь без ролей входит, но не получает ни одной операции.

#### Scenario: Пользователь совмещает роли

- **WHEN** входит пользователь с ролями Администратора и Учителя
- **THEN** ему доступны операции обеих ролей одновременно
- **AND** переключение между ролями нигде не требуется

#### Scenario: Учитель обращается к операции Администратора

- **WHEN** пользователь с ролью Учителя обращается к операции, требующей роли
  Администратора
- **THEN** операция не выполняется
- **AND** отказ происходит независимо от того, показана ли эта операция
  пользователю

#### Scenario: Пользователь без ролей

- **WHEN** входит пользователь, которому не назначено ни одной роли
- **THEN** вход выполняется
- **AND** ни одна операция ему не доступна

### Requirement: Система с первого запуска имеет одного Администратора

После применения миграций к пустой базе система SHALL содержать ровно одну
учётную запись — с ролью Администратора и признаком «пароль подлежит смене».
Ни одного шага настройки, выполняемого вручную, для этого не требуется.

#### Scenario: Первый запуск на пустой базе

- **WHEN** система впервые запускается на базе, где нет ни одной таблицы
- **THEN** в ней существует учётная запись с ролью Администратора
- **AND** её пароль помечен подлежащим смене

#### Scenario: Повторный запуск

- **WHEN** система запускается на базе, где эта учётная запись уже есть
  и её пароль сменён
- **THEN** учётная запись не создаётся заново
- **AND** сменённый пароль остаётся действующим

### Requirement: Пароль, назначенный не владельцем записи, подлежит смене при первом входе

Пароль, который пользователь не задавал сам — заведённый вместе с учётной
записью или сброшенный Администратором, — SHALL быть помечен подлежащим смене.
Пользователь с таким паролем MUST входить, но до смены пароля ему доступны
только форма смены пароля и выход; любое другое обращение MUST приводить
к форме смены пароля.

Проверка выполняется прежде проверки прав по ролям: иначе ограничение
обходится обращением по прямому адресу.

#### Scenario: Первый вход с назначенным паролем

- **WHEN** пользователь входит паролем, помеченным подлежащим смене
- **THEN** он попадает на форму смены пароля

#### Scenario: Попытка обойти смену пароля

- **WHEN** пользователь с паролем, подлежащим смене, обращается к любой другой
  странице системы напрямую
- **THEN** он получает форму смены пароля
- **AND** запрошенная страница не показывается, даже если его роли её допускают

#### Scenario: Пароль сменён

- **WHEN** пользователь задаёт новый пароль
- **THEN** пометка снимается
- **AND** дальнейшая работа идёт по правам его ролей

### Requirement: Пользователь меняет свой пароль

Система SHALL позволять вошедшему сменить собственный пароль, подтвердив
знание текущего. Новый пароль MUST храниться невосстановимо, как и прежний.

#### Scenario: Смена пароля

- **WHEN** вошедший вводит текущий пароль и новый
- **THEN** пароль заменён
- **AND** следующий вход возможен только новым паролем

#### Scenario: Текущий пароль указан неверно

- **WHEN** вошедший вводит неверный текущий пароль
- **THEN** пароль не заменён
- **AND** пользователю сообщается об отказе

### Requirement: Администратор ведёт учётные записи

Администратор SHALL иметь возможность увидеть список учётных записей, завести
новую с именем входа и начальным паролем, назначить и снять роли, сбросить
пароль. Сброшенный пароль MUST помечаться подлежащим смене.

Имя входа MUST быть уникальным: попытка завести запись с занятым именем
отклоняется. Учётные записи MUST быть доступны только роли Администратора:
пользователю с ролью Учителя они не видны и не изменяемы.

Удаления учётных записей в системе не предусмотрено: за учителем стоят его
ученики, работы и отметки, и вопрос об их судьбе решается отдельно.

#### Scenario: Заведение пользователя

- **WHEN** Администратор заводит учётную запись с новым именем входа
  и начальным паролем
- **THEN** запись создана
- **AND** её пароль помечен подлежащим смене
- **AND** названный пользователь может войти этим паролем

#### Scenario: Имя входа занято

- **WHEN** Администратор заводит учётную запись с именем, которое уже
  используется
- **THEN** запись не создаётся
- **AND** Администратору сообщается о занятом имени

#### Scenario: Назначение и снятие роли

- **WHEN** Администратор назначает пользователю роль либо снимает её
- **THEN** набор прав пользователя меняется соответственно

#### Scenario: Сброс пароля

- **WHEN** Администратор задаёт пользователю новый пароль
- **THEN** прежний пароль перестаёт действовать
- **AND** новый пароль помечен подлежащим смене

#### Scenario: Учитель обращается к учётным записям

- **WHEN** пользователь с ролью Учителя, но без роли Администратора,
  обращается к списку учётных записей или к операции над ними
- **THEN** доступ не предоставляется
