## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь — как это
ложится на существующий код.

Что уже есть:

- `MasteryRepository.findByStudent(UserId, StudentId) → Map<Cell, MasteryStatus>`
  отдаёт все суждения владельца об Ученике одним запросом; ячейки без
  строки в карте отсутствуют — это и есть `неизвестно` (ADR-0039).
  Больше ни одного запроса к отметкам экрану не нужно.
- Ячейки порождены разметкой (инвариант 4): пара «Тема × Метод»
  существует, если есть Задача с обеими метками. У `ProblemRepository`
  есть образец этого вопроса по одной Теме — `findMethodsUsedInTopic`
  (`problem_topic ⋈ problem_solution_method` по `problem_id`).
- Дерево — `TaxonomyService.tree() → List<TaxonomyBranch>` от корней,
  `paths()` — полные пути узлов; Методы — `SolutionMethodService.all()`.
  Всё это — общая библиотека, читается любым вошедшим без владельца.
- Поиск — `GET /problems?node=<id>&method=<id>`; `ProblemFilter`
  с самого начала строился под «второй вход — подбор по пробелам».
- Карточка Ученика (`templates/student/student.html`) ведёт на соседние
  области **только адресами** («Задания Ученика», «Работы Ученика»):
  область Учеников о них в коде не знает.
- `MasteryService` берёт владельца из `CurrentUser`; Ученика по
  идентификатору отдаёт `StudentService.student(id)` — чужой неотличим
  от несуществующего (`StudentNotFoundException` → 404), как
  в `StudentWorkService.ofStudent`. Кольца бинов нет: `StudentService`
  собирает `List<StudentUsage>`, а `MasteryOfStudent` зависит
  от репозитория, не от `MasteryService`.

Ограничения: ADR-0011 запрещает таблицу владения **как форму**; ADR-0013 —
единое значение; шаблоны не вычисляют (standards.md); Администратор
личного контура не видит (ADR-0005).

## Goals / Non-Goals

**Goals:**

- Один экран чтения `GET /mastery?student=` в существующей области
  `ru.locus.mastery`, без миграций: всё вычисляется в запросе.
- Одна новая операция чтения в `MasteryService`; один новый вопрос
  библиотеки в `ProblemRepository`; шаблон; ссылка на карточке Ученика.
- Тест, сторожащий «единого значения нет».

**Non-Goals:**

- Правка отметок с этого экрана — никогда (ADR-0011).
- Ученик, протаскиваемый сквозь поиск в форму выдачи; сводки по Группе;
  теория по пробелам.
- Изменения в `library-search`, `taxonomy`, `students-groups` сверх одной
  ссылки в шаблоне.

## Decisions

### Где живут данные

Экран — **личный контур, читающий библиотеку**. Отметки — по владельцу
всегда (`findByStudent(owner, student)`); Ученик — по владельцу
(`StudentService.student`); дерево, пути, Методы и пары разметки —
из общей библиотеки **без** владельца (ADR-0027). Менять с экрана нельзя
ничего. Ни один новый метод репозитория личного контура не появляется;
новый метод `ProblemRepository` — библиотечный, параметра владельца
не принимает и не должен.

### Вопрос библиотеки: `ProblemRepository.findMethodsUsedByTopic()`

```
select distinct pt.topic_id, psm.solution_method_id
from problem_topic pt
join problem_solution_method psm on psm.problem_id = pt.problem_id
```

→ `Map<TaxonomyNodeId, List<SolutionMethodId>>` — Тема → Методы, которыми
размечена хотя бы одна её Задача. Один запрос на весь каталог, а не
`findMethodsUsedInTopic` по каждой Теме дерева: у экрана все Темы сразу,
и N запросов на N Тем — лишнее. Открыт через `ProblemService`
(без `@PreAuthorize`, как остальное чтение библиотеки).

Почему карта, а не список пар: третьей записи «пара» (`mastery.Cell`,
`work.ProblemPair` уже есть) не заводится; форма «Тема → её Методы» —
ровно то, что нужно для ячеек Темы, и чужих типов `problem` не тянет.

### Ячейки Темы = пары разметки ∪ пары с суждением

Ячейки Темы для данного Ученика — Методы из `findMethodsUsedByTopic`
для этой Темы плюс Методы из `findByStudent`, у которых `topic` — эта
Тема. Второе слагаемое — замыкание правила, а не ожидаемый случай:
сегодня суждение без Задачи возникнуть не может (отметка ставится
по Работе на замороженной Задаче, перестройка двигает Задачи и отметки
вместе), но `method-edit-impact` ещё не решён, и распределение не должно
терять суждение молча, если оно появится. Ячейка без суждения —
`неизвестно`.

### `Distribution` — четыре `int`, никакого значения

```java
record Distribution(int mastered, int uncertain, int notMastered, int unknown)
    plus(Distribution)   // для суммирования по поддереву и по Методу
    cells()              // сумма четырёх — «ячеек нет», если 0
    static of(Collection<MasteryStatus>) // из статусов ячеек
```

Имя — из глоссария: `Distribution` зарезервировано за агрегатом владения
(glossary.md, «Имена»). У записи **нет и не будет** метода, возвращающего
`MasteryStatus`, доли, балла или «итога» — это сторожит
`NoSingleMasteryValueTest` отражением по `Distribution` (ни одного метода
с возвращаемым типом `MasteryStatus`, `double`, `float`) и по шаблону
(четыре числа у каждого узла с ячейками). ADR-0013 отвергает и правило
слияния как агрегат, и числовой показатель.

Распределение Раздела — `plus` по потомкам. Это верно без двойного счёта:
ячейка принадлежит ровно одной Теме, Тема — ровно одному родителю
(инвариант 8). Распределение Метода — `plus` по всем Темам, где Метод
среди ячеек.

### Вид экрана: `MasteryOverview` — собирается сервисом, шаблон только показывает

```
MasteryOverview(Student student,
                List<MasteryBranch> tree,        // дерево целиком, от корней
                List<MasteryOfMethodRow> methods,// Методы с ячейками, по имени
                List<Gap> gaps)                  // не владеет, по пути Темы и имени Метода

MasteryBranch(TaxonomyNode node, Distribution distribution, List<MasteryBranch> children)
MasteryOfMethodRow(SolutionMethod method, Distribution distribution)
Gap(TaxonomyNodeId topic, String topicPath, SolutionMethodId method, String methodName)
```

- Дерево целиком, а не проваливание по узлам: учителю нужна картина
  по Ученику, а не навигация; узел без ячеек показывается с «ячеек нет»
  (`cells() == 0`), не скрывается — скрытый Раздел выглядел бы
  как отсутствующий в библиотеке.
- В таблице Методов — только Методы, у которых есть хоть одна ячейка
  (в разметке или с суждением): Метод без ячеек не «неизвестен», у него
  нечего распределять.
- Пробелы — строки `findByStudent` со статусом `NOT_MASTERED`, с полным
  путём Темы (`TaxonomyService.paths()`) и именем Метода; порядок — по пути
  Темы, затем по имени Метода. Ссылка в поиск строится в шаблоне
  `@{/problems(node=…, method=…)}` — это адресация, не вычисление,
  как ссылки на карточке Ученика.

Сборка — в `MasteryService.overviewOf(StudentId)`,
`@PreAuthorize("hasRole('TEACHER')")`: три чтения библиотеки (дерево
с путями, Методы, пары разметки), одно чтение отметок, обход дерева.
Ни счётчиков в шаблоне, ни условий «если статус такой-то» — только
`th:text` четырёх чисел и `th:each`.

### Вход: `GET /mastery?student=` в `MasteryController`

Контроллер уже есть (`POST /mastery`); добавляется `GET` с параметром
`student` → `mastery/student.html`; без параметра — `redirect:/students`
(вход на экран идёт от Ученика, как вход в Работы — от Задания).
`StudentNotFoundException` не перехватывается — 404 от сервиса, чужой
Ученик неотличим от несуществующего. Контроллер остаётся тонким:
`MasteryControllerIsThinTest` продолжает проходить.

Альтернатива `/students/{id}/mastery` отвергнута: область Учеников
не знает отметок, и адрес отметок принадлежит их области; `/works?student=`
— тот же образец.

### Ссылка на карточке Ученика

`templates/student/student.html`: `<a href="/mastery?student=…">Владение
Ученика</a>` рядом с Заданиями и Работами. Только адрес, как и у соседей:
`student` о `mastery` в коде не знает.

### Тесты

- `MasteryOverviewTest` — сервис: распределение по Теме (с `неизвестно`
  из разметки); по Разделу — сумма поддерева; по Методу — сквозь Темы;
  «семь и один» против «один и семь»; ячейка не из разметки не считается;
  узел без ячеек — `cells() == 0`; пробелы — только `NOT_MASTERED`,
  с путём и именем; чужой Ученик — `StudentNotFoundException`; отметки
  другого Учителя не считаются (дополняет `MasteryIsFilteredByOwnerTest`).
- `MasteryOverviewScreenTest` — экран: четыре числа у узла; «ячеек нет»
  у пустого; ни одного `<form>` и `<select>`; ссылка пробела ведёт на
  `/problems?node=T&method=M`, и по ней находится Задача; ссылка
  с карточки Ученика.
- `NoSingleMasteryValueTest` — отражение по `Distribution`.
- `MasteryAccessTest` — `GET` Администратору отклонён, Учителю доступен,
  без входа — форма входа.
- `OwnerIsRequiredByMasteryTest` — не меняется: новых методов
  у `MasteryRepository` нет; `ProblemRepository` — библиотека.

## Risks / Trade-offs

- [Дерево целиком на одном экране при большом рубрикаторе] → дерево
  Разделов и Тем в первой версии — десятки узлов, не тысячи; проваливание
  по узлам добавляется потом без смены модели (`MasteryBranch` уже
  рекурсивна).
- [Пути Тем через `paths()` — второй обход дерева] → дерево небольшое;
  пути нужны только пробелам, а `paths()` уже есть и проверен;
  свой обход ради экономии одного запроса не стоит второй реализации.
- [`neизвестно` считается от разметки: правка разметки задним числом
  меняет распределение] → это и есть смысл ячеек по употреблению
  (инвариант 4); суждения при этом не теряются (объединение с парами
  с суждением); поведение при правке Методов — `method-edit-impact`.
- [Пробел ведёт в поиск, но Ученика в форму выдачи учитель выбирает сам]
  → сознательно вне объёма (proposal.md); один лишний выбор в списке.
