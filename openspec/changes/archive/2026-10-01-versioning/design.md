## Context

Версии нет (см. proposal.md — Why). Единица работы — изменение OpenSpec;
они идут строго по очереди, по одному (`backlog-batch` гоняет их
последовательно), поэтому конфликта за номер версии не бывает.

Что есть: `pom.xml` (версия `0.0.1-SNAPSHOT`, у `spring-boot-maven-plugin`
целей нет); шапка страниц — `templates/fragments/shell.html`, данные —
`ShellAdvice.java`. Шапки у посетителя без входа нет (`shell == null`),
поэтому подвал не может питаться от `shell`. Полностраничных шаблонов — 24,
все берут `fragments/shell :: head` (кроме двух вставок: `mastery/parts.html`,
`taxonomy/branches.html`); у формы входа и страницы ошибок — тоже.

Развёртывания пока нет: схема обновления «с остановкой» (ADR-0024), откатных
миграций нет (ADR-0023). Версия приложения и версия схемы БД — разные вещи;
схему по-прежнему ведёт Liquibase, и версию схемы в подвале не выводим.

## Goals / Non-Goals

**Goals:**
- Один источник правды о версии — `pom.xml`; подвал и тег не могут разойтись
  с ним без правки руками.
- По версии и хешу в подвале можно найти коммит и запись в `CHANGELOG.md`.
- Правило уровня применимо без обсуждения: по виду изменения (есть дельта
  спек, ломает ли) уровень вычислим.

**Non-Goals:**
- Автоматический подъём версии и релиз-инструменты (`maven-release-plugin`):
  изменений один-два в неделю, ритуал короткий, и автомат даёт больше
  движущихся частей, чем экономит.
- Публикация собранных артефактов (jar, образы); отправляются только теги.
- Версия API: внешнего API нет.
- Показ версии схемы БД и времени сборки.

## Decisions

**Версия без `-SNAPSHOT`, поднимается внутри изменения.** Работы линейны,
поэтому «разрабатываемая» версия не нужна: `develop` всегда равен последнему
завершённому изменению. Альтернатива — `X.Y.Z-SNAPSHOT` с отдельным ритуалом
релиза — нужна, когда несколько изменений копятся до выкладки; владелец
выбрал «релиз равен изменению», и ритуал ушёл. Цена: версия на `develop`
в середине изменения равна предыдущей — подвал в разработке показывает
последнюю завершённую, а не «будущую».

**Уровень определяется в `proposal.md`, применяется последним пунктом
`tasks.md`.** Решение принимается, когда виден объём (при `propose`), а не
по ходу кода; исполнитель не придумывает номер, а подставляет записанный
уровень. Если по ходу реализации объём изменился, уровень правится
через `/opsx:update` — так же, как прочие артефакты.

**Правила уровня.** `MAJOR` — крупное изменение, которое Учитель замечает
целиком (новый интерфейс вроде `ui-redesign`, большая возможность — целая
область), либо обновление требует действий оператора или необратимо меняет
данные (признак — «Ломает: да» в таблице бэклога); `MINOR` — есть дельта
спек, но изменение не крупное; `PATCH` — исправление без дельты; «без
изменения» — только документы и оснастка. Конфликт признаков решается старшим
уровнем. «Крупное» не вычисляется: оно суждение, поэтому `MAJOR` предлагается
при `propose` и подтверждается владельцем; остальные уровни выводятся по
признакам. Начальная версия `1.0.0` не привязана к выкладке на стенд: версию
дают изменения, а не событие эксплуатации.

**Тег ставится на коммит архивации.** Именно в нём `openspec/specs/` и код
согласованы, и `pom.xml` уже имеет новую версию. Имя — `vX.Y.Z`, тег
аннотированный (`git tag -a`), с одной строкой из `CHANGELOG.md`. Тег
отправляется в `origin` сразу после коммита архивации (`git push origin vX.Y.Z`):
владелец разрешил это постоянным правилом. Опубликованный тег не
переставляется и не удаляется — для чужих клонов он необратим; ошибка в версии
исправляется следующей версией, а не переносом тега.

**`CHANGELOG.md` — в корне, по-русски, одна строка на изменение.** Новая
запись сверху: `## 1.0.0 — 2026-10-01` и список «изменение — что изменилось
для Учителя/оператора». Строка берётся из «Why»/«What Changes» предложения,
а не сочиняется заново. Альтернатива «генерировать из архива» отвергнута:
архив пишется для разработчика, а журнал — для того, кто смотрит
на подвал; фраза у них разная.

**Подвал — фрагмент `shell :: footer`, подключаемый каждой страницей.**
Данные — атрибут модели `build` (`record Build(String version, String
commit)`) в отдельном `@ModelAttribute` в `ShellAdvice` (не в `shell`, который
для посетителя без входа `null`). Версия — из бина `BuildProperties`
(цель `build-info` в `spring-boot-maven-plugin`: версия берётся из `pom.xml`),
хеш — из `GitProperties` (плагин `git-commit-id-maven-plugin`,
`failOnNoGitDirectory=false`, `abbrevLength=7`, формат `git.properties`
под Spring Boot). Оба бина берутся через `ObjectProvider`: нет метаданных —
подвал показывает то, что есть. Альтернативы:
- *Включать подвал через `Filter`, дописывающий HTML в ответ* — отвергнуто:
  это скрытая подмена тела ответа, ломающая просмотр PDF и файлов.
- *Вставлять подвал JavaScript-ом* — отвергнуто: запрет встроенных скриптов
  (ADR-0041) и пустой подвал при отключённом JS.
- *Только в шапке* — отвергнуто: у формы входа и ошибок шапки нет.
- *Actuator `/actuator/info`* — отвергнуто: новая зависимость и ещё один
  адрес, а видеть версию нужно на странице, не по отдельному запросу.

**Охранный тест по шаблонам.** Тест читает `templates/**/*.html` и требует
у каждого, кто подключает `fragments/shell :: head`, подключение
`fragments/shell :: footer`; сам фрагмент и вставки без `<html>` исключены
по признаку «в файле нет подключения `head`». Так же устроены прочие
охранные тесты проекта (`…IsNot…Test`): забытый подвал на новой странице
— тихая ошибка, а тест её громкая.

**Граница общего и личного.** Данных нет: версия и хеш — свойства сборки,
не лежат ни в библиотеке, ни в личном контуре, не правятся из интерфейса,
фильтра по владельцу нет.

**Проверка по `antipatterns.md`.** Свои `<style>` и скрипты в шаблонах не
заводятся — стиль подвала идёт в `locus.css`; тихого отказа нет — отсутствие
хеша показывается как отсутствие, а не как пустой «·».

## Risks / Trade-offs

- [Версию забыли поднять в `pom.xml`] → последний пункт `tasks.md` и правило
  `config.yaml` для `tasks`; расхождение видно в подвале и `CHANGELOG.md`.
- [Подвал на новой странице забыт] → охранный тест по шаблонам.
- [В сборке из tarball без `.git` нет хеша] → подвал показывает версию без
  хеша; сборка не падает (`failOnNoGitDirectory=false`).
- [Подвал в разработке показывает версию предыдущего изменения] → принято
  сознательно (см. решение о `-SNAPSHOT`); хеш в подвале всё равно ведёт
  к точному коммиту.
- [Тег поставлен на неверный коммит и уже отправлен] → не переставлять;
  выпустить следующий `PATCH`. Перед отправкой — проверить, что тег
  указывает на коммит архивации (`git show vX.Y.Z`).

## Migration Plan

Миграций БД нет. Версия `1.0.0` ставится самим изменением. Стенд, поднятый
владельцем вне бэклога, работает на сборке с `0.0.1-SNAPSHOT` и без подвала:
версию он покажет после первой выкладки сборки с этим изменением, отдельного
переходного периода нет. Откат — обычный `git revert`.
