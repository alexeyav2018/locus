# Design

## Context

Мотивация — proposal.md, «Why». Что уже есть и что определяет подход:

- **Личность — только через `CurrentUser`** ([ADR-0027](../../context/adr/0027-mehanizm-granicy-obshchego-i-lichnogo.md)):
  `CurrentUser.loggedIn()` читает `Authentication` из `SecurityContextHolder`
  и ищет запись по имени входа (`CurrentUser.java:46`). Сервисы берут
  владельца оттуда, `@PreAuthorize("hasRole('ADMINISTRATOR')")` стоит
  на методах. Значит, инструменту достаточно поставить в контекст
  безопасности **ту же** `Authentication`, что ставит вход формой
  (имя входа и `ROLE_…`, `AccountDetailsService.java:44`), — и весь
  сервисный слой заработает без изменений.
- **Сервисы уже умеют почти всё нужное**: `TaxonomyService.topicPaths`,
  `SolutionMethodService.all`, `CharacteristicService.all`,
  `ProblemService.search/problems/create`, `FilePages.page/outline`,
  `AssemblyDraftService.preview`. Нет двух методов: списка своих
  черновиков и куска страницы черновика картинкой.
- **Java SDK MCP 2.1.0** (`io.modelcontextprotocol.sdk:mcp`): servlet
  транспорты лежат в `mcp-core` — `HttpServletStatelessServerTransport`
  (без сессий) и `HttpServletStreamableServerTransportProvider`
  (с сессиями); JSON — `mcp-json-jackson3` на Jackson 3, который
  и так у Spring Boot 4. Синхронный обработчик инструмента SDK
  запускает **на другом потоке** (`Schedulers.boundedElastic`,
  `McpStatelessServerFeatures.java:230`), а не на потоке сервлета;
  в обработчик приходит `McpTransportContext`, который транспорт
  извлекает из запроса на потоке сервлета (`contextExtractor`).
  Клиент того же SDK (`HttpClientStreamableHttpTransport`,
  `McpClient.sync`) — готовый тест-двойник.
- Claude Code подключает сервер по `.mcp.json` с `headers`
  и подстановкой переменных окружения; это свойство измеряет
  `agent-spike`, здесь оно не проверяется.

**Граница общего и личного.** Инструменты библиотеки (дерево, словари,
Задачи) — общее: читают все вошедшие, фильтра по владельцу нет;
`create_problem` — Администратор, проверка — `@PreAuthorize` сервиса.
Инструменты Черновиков сборки — личное у загрузившего: владелец
подставляется `AssemblyDraftService` из `CurrentUser`, репозиторий
получает новый метод `findByOwner(UserId)` — с владельцем, как все
методы личного контура ([ADR-0027](../../context/adr/0027-mehanizm-granicy-obshchego-i-lichnogo.md)).
Токен — не данные: живёт в памяти, в базу не попадает. Собственных
проверок прав у инструментов нет ([ADR-0056](../../context/adr/0056-pomoshchnik-vtoroj-klient-servisnogo-sloya.md)).

Проверено по `antipatterns.md`: фильтр к библиотеке не применяется;
на черновиках не забыт — его держит сервис; интерпретации содержимого
нет — кусок по Рамке режется как коробка, страница отрисовывается
как на экране; фонового процесса нет — токены не чистятся по расписанию,
истёкший просто отклоняется, а отозванный удаляется при отзыве.

## Goals / Non-Goals

**Goals:** Помощник (пока — тест-двойник клиента) действует в библиотеке
и в своих черновиках через `/mcp` под личностью учителя; ни один вызов
не проходит без живого токена; реестр — единственный список
инструментов, и сервер отдаёт ровно его; SDK MCP виден только
`ru.locus.assistant`.

**Non-Goals:** запуск процесса Claude Code и выпуск токена на настоящую
Реплику (`agent-runner`); экран и хранение Разговоров (`assistant-chat`);
Черновик Задачи и его инструменты (`problem-intake`); текст Задачи
(`problem-text`); инструменты личного контура (по одному элементу
на область, ADR-0054); загрузка черновика инструментом (Р4);
проверка совместимости Claude Code с сервером без сессий (Р2, риск).

## Decisions

Решения, принятые сессией батча без вопроса владельцу: у каждого есть
предпочтительный вариант, обоснованный документами. Владелец видит их
здесь.

### Р1. SDK MCP — `io.modelcontextprotocol.sdk:mcp` 2.1.0, виден только `ru.locus.assistant`

Под вопросом: какой библиотекой строить сервер. Варианты: (а) сам SDK
MCP; (б) Spring AI со стартером MCP-сервера; (в) свой JSON-RPC поверх
Spring MVC. Выбрано (а): ADR-0054 называет «Java SDK MCP» прямо; Spring AI
принесла бы вторую большую зависимость ради одной автоконфигурации
и свои версии Jackson; свой JSON-RPC — вторая оснастка, которую некому
держать (П4). Версия 2.1.0 — последняя выпущенная; её BOM `mcp-bom`
управляет частями. Как SDK хранилища виден только `ru.locus.file`
(standards.md, «Файлы»), так типы SDK MCP (`McpSchema`, транспорт,
сервер) видны только пакету `ru.locus.assistant`: области объявляют
инструменты через свою абстракцию (Р6), и смена SDK — правка одного
пакета. Это записывается в `standards.md`.

### Р2. Транспорт — Streamable HTTP **без сессий**, `/mcp` на том же порту; замок — токен, не loopback

Под вопросом: форма сетевой поверхности. Варианты транспорта:
(а) `HttpServletStatelessServerTransport` — без сессий, каждый вызов
самодостаточен; (б) `HttpServletStreamableServerTransportProvider` —
с сессиями `Mcp-Session-Id`, уведомлениями сервера и keep-alive.
Выбрано (а): между Репликами на стенде не должно работать ничего
(ADR-0054), а сессия — ровно то, что переживает вызов и требует
уборки; уведомлений сервера Помощнику не нужно. Протокол позволяет
серверу не выдавать идентификатор сессии; клиент SDK это принимает
(`HttpClientStreamableHttpTransport.java:525`), совместимость
Claude Code — риск ниже.

Варианты адреса: (а) путь `/mcp` на порту приложения; (б) второй
разъём Tomcat, привязанный к `127.0.0.1`. Выбрано (а). «HTTP
на loopback» в ADR-0054 — маршрут агента: `.mcp.json` рабочего места
(`agent-runner`) укажет `http://127.0.0.1:<порт>/mcp`. Проверять
loopback на стороне Локуса бессмысленно: за обратным прокси стенда все
запросы приходят с loopback, а второй разъём — вторая конфигурация
сервера ради проверки, которая ничего не проверяет. Замок один — токен
(Р3); без него `/mcp` отвечает `401` кому угодно, в том числе
с loopback. Проверка заголовков `Host`/`Origin` SDK (защита от DNS
rebinding) не включается: сервер не отдаёт ничего без токена,
а список допустимых хостов пришлось бы вести в конфигурации стенда.

### Р3. Личность — токен в памяти, своя цепочка безопасности для `/mcp`, перенос `Authentication` в поток обработчика

Под вопросом: как инструмент узнаёт учителя и как это доходит до
`CurrentUser`. Выбрано:

- `TurnTokens` (`ru.locus.assistant`) — хранилище токенов в памяти
  (`ConcurrentHashMap`): `issue(UserId, Duration) → TurnToken`,
  `resolve(String) → Optional<UserId>` (истёкший отклоняется и удаляется),
  `revoke(TurnToken)`. Значение — 32 случайных байта в base64url,
  сравнение через хранилище. В базу не пишется: токен должен умереть
  с процессом (ADR-0057), а запись пережила бы перезапуск.
- `TurnTokenFilter` на `/mcp`: читает `Authorization: Bearer`, по
  `resolve` берёт `User` из `UserRepository` и ставит
  в `SecurityContextHolder` ту же `Authentication`, что ставит вход
  формой (`UsernamePasswordAuthenticationToken.authenticated(login, null,
  ROLE_…)`). Нет токена или не разрешился — `401` с `WWW-Authenticate:
  Bearer`, без перенаправления на форму входа.
- Вторая `SecurityFilterChain` с `@Order` раньше основной:
  `securityMatcher("/mcp")`, без CSRF (запросы не из браузера,
  пропуск — токен), без HTTP-сессии (`STATELESS`), без
  `PasswordChangeFilter` — учётной записи с паролем к смене недоступна
  ни одна страница, значит, и Реплику ей не начать; `anyRequest().authenticated()`.
  Основная цепочка не меняется.
- Обработчик инструмента SDK выполняет на другом потоке, и `ThreadLocal`
  контекста безопасности туда не доходит. Поэтому `contextExtractor`
  транспорта кладёт `Authentication` из контекста потока сервлета
  в `McpTransportContext`, а обёртка каждого инструмента (одна,
  в `ru.locus.assistant`) ставит её в `SecurityContextHolder` на время
  вызова и снимает после. `CurrentUser` не меняется и остаётся
  единственным, кто знает о вошедшем: ему всё равно, кто поставил
  `Authentication` — форма или токен.

Отклонено: передавать `UserId` параметром в сервисы (против ADR-0027);
служебный пользователь «Помощник» (ADR-0057); хранить токен в базе
(переживёт перезапуск); отдельный `AuthenticationProvider` Spring
Security с `Bearer`-ресурс-сервером — машинерия OAuth ради одного
заголовка и одного хранилища в памяти.

### Р4. Состав первой очереди: десять инструментов; загрузки нет, `create_problem` — из строк сборки

Карточка перечисляет «Черновики сборки (список, загрузка, страница
картинкой, кусок по рамке)» и «Задачи (чтение, создание с текстом,
страницы PDF картинкой)». Два отступления:

- **Загрузки черновика инструментом нет.** Процесс в клетке не имеет
  файлов и сети (ADR-0057): единственное, откуда модель могла бы взять
  байты, — её собственный контекст, то есть снимок прошёл бы через
  модель как base64 туда и обратно. Снимок кладёт черновиком форма
  страницы Помощника (`assistant-chat`: «загружен черновик N»), и список
  черновиков — то, чем Помощник его находит.
- **`create_problem` заводит Задачу из строк сборки уже сейчас,** текст
  добавится с `problem-text`. У `ProblemPdf` два варианта — готовый файл
  и порядок сборки; файла у модели нет, порядок сборки есть. Это даёт
  сквозной путь «снимок → кусок по Рамке → Задача» до текста
  и проверяет `@PreAuthorize` сервиса на втором клиенте. Инструмент
  зовёт тот же `ProblemService.create`, что форма.

Инструменты Черновика Задачи — при `problem-intake`, когда появится
сущность; инструменты личного контура — отдельными элементами
(ADR-0054, последствия). `get_assembly_draft_page` отдаёт обычный
размер (1600 px по длинной стороне): модель крупнее не видит, а для
мелкого почерка есть `crop_assembly_draft_page`.

### Р5. Форма ответов: JSON текстом, страницы — JPEG, отказ — результат с признаком ошибки

Данные (списки, Задача, номер заведённой) возвращаются одним текстовым
содержимым — JSON, собранным тем же `JsonMapper` приложения из записей
с плоскими полями (`long`, `String`, списки): идентификаторы-обёртки
проекта наружу не идут. Страница и кусок — `ImageContent` JPEG
в base64. Отказ сервиса (`IllegalArgumentException`,
`*NotFoundException`, `AccessDeniedException`, `NotATopicException`
и прочие `RuntimeException` с текстом для человека) — `CallToolResult`
с `isError` и текстом сообщения; `Optional.empty()` от
`AssemblyDraftService.preview` и `FilePages.page` — тот же отказ
«страницы нет», одинаковый для чужого и несуществующего. Соединение
не рвётся: модель читает отказ и действует дальше, как учитель читает
красную строку на странице. Неожиданная ошибка (`IOException` в обёртке,
NPE) — тоже `isError`, но с общим текстом «не удалось выполнить» и записью
в журнал: текст исключения не для человека, а внутренности
стенда наружу не идут.

Отклонено: `structuredContent` с JSON-схемой результата — вторая схема
на каждый инструмент при том же содержимом; текст-таблицы «для чтения» —
модель читает JSON не хуже, а разбирать его проще.

### Р6. Абстракция инструмента и реестр

В `ru.locus.assistant`: `Tool` (имя, описание, схема аргументов,
обработчик `Arguments → ToolResult`), `ToolResult` (`json(Object)`,
`image(byte[])`, `refusal(String)`), `Arguments` (разбор `Map<String,
Object>` из JSON: `requireLong`, `optionalLong`, `longs`, `string`,
`optionalInt`; отсутствующий или не того типа аргумент — отказ, называющий
его имя), `Schema` (короткие конструкторы JSON-схем: `object`, `integer`,
`string`, `array`, `required`), интерфейс-вопрос `Tools` (`List<Tool>
tools()`) и `ToolRegistry`, собирающий реализации списком — как
`NodeContent`, не зная ни одной по имени. Области реализуют `Tools`
рядом с контроллерами: `TaxonomyTools`, `DictionaryTools`,
`ProblemTools`, `AssemblyDraftTools`. Направление зависимости —
от области к `ru.locus.assistant`, как от области к Spring MVC;
`ru.locus.assistant` от областей не зависит.

`McpServerConfiguration` строит из реестра `SyncToolSpecification`
SDK: обёртка переводит `Tool` в `McpSchema.Tool`, аргументы — в
`Arguments`, результат — в `CallToolResult`, и переносит `Authentication`
(Р3). Тесты: `ToolRegistryTest` (имена неповторимы, латиница
`snake_case`, ровно десять); `ToolsAreThinTest` (классы инструментов
не держат репозиториев и `FileStorage`); `EveryToolAnswersTheClientTest` —
клиент SDK по HTTP перечисляет и зовёт каждый инструмент реестра,
и тест падает, если в реестре есть инструмент, которого он не позвал.

### Р7. Кусок страницы черновика — отрисовка крупно и обрезка растра

`PdfAssembly.previewPiece(file, name, kind, page, frame)`: страница
отрисовывается как для крупного показа (`PreviewSize.LARGE`, 3200 px),
из растра вырезается прямоугольник Рамки в долях, и результат
ужимается до обычного предела (1600 px по длинной стороне), если
крупнее. Так четверть страницы приходит модели в том же разрешении,
что и целая, а мелкий почерк читается. Это не векторная обрезка
ADR-0045 — там кусок ложится в PDF, здесь только показывается; режется
картинка, то есть коробка, содержимое не интерпретируется.
`AssemblyDraftService.previewPiece(id, page, frame)` — с владельцем
из `CurrentUser`, `Optional.empty()` для чужого, несуществующего
и страницы вне черновика, как `preview`.

### Р8. Список своих черновиков

`AssemblyDraftRepository.findByOwner(UserId)` — черновики владельца
в порядке загрузки; `AssemblyDraftService.own()` — с `@PreAuthorize`
Администратора и владельцем из `CurrentUser`, с попутной уборкой
по сроку (`sweep`), как `upload`: список — открытие инструмента.
Метод с `UserId` — в `OwnerIsRequiredByDraftsTest` ничего не меняется.

## Risks / Trade-offs

- [Claude Code может ожидать сервер с сессиями] → протокол допускает
  сервер без `Mcp-Session-Id`, клиент SDK работает; если `agent-runner`
  при подключении настоящего Claude Code упрётся, транспорт меняется
  на `HttpServletStreamableServerTransportProvider` внутри
  `McpServerConfiguration` — абстракция Р6 и тесты от транспорта
  не зависят.
- [Картинка в результате инструмента может быть не видна модели
  в неинтерактивном режиме] → измеряет `agent-spike`; запасной путь —
  инструмент возвращает текст-ссылку на страницу просмотра, но это
  решение `agent-runner`, не этого элемента.
- [Обработчик на чужом потоке: забытый перенос `Authentication`
  оставляет инструмент без вошедшего] → ошибка громкая, не тихая:
  `CurrentUser.account()` бросает `NotLoggedInException`, `@PreAuthorize`
  отклоняет; тест-двойник зовёт каждый инструмент и упадёт.
- [Токен в заголовке попадёт в журналы прокси] → токен живёт минуты
  и мёртв после Реплики; журналы — эксплуатация (ADR-0051).
- [`find_problems` без условий отдаёт всю библиотеку одним JSON] →
  то же делает страница поиска; библиотека измеряется сотнями Задач,
  JSON — сотнями килобайт; предел не ставится, пока не понадобится.
- [Защита от DNS rebinding выключена] → без токена сервер не отдаёт
  ничего; токен браузеру неизвестен; рубежом служит он.

## Migration Plan

Схема базы не меняется; новых свойств конфигурации нет: токены живут
в памяти, срок задаёт выпускающий. Выкладка — обычная, с остановкой
(ADR-0024). Откат — предыдущая версия; данных, которые пришлось бы
возвращать, изменение не создаёт.
