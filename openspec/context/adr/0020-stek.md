# ADR-0020. Стек — Java 21, Spring, Thymeleaf, PostgreSQL, развёртывание на VPS

## Контекст

Выбор стека значился первым в списке нерешённых вопросов `CLAUDE.md`. К моменту
выбора предметная область оказалась технически скромной: после принятых решений
отпали рендеринг формул, автопроверка, фоновый планировщик, уведомления,
учётные записи учеников и приём файлов от них. Осталось хранение и правка
карточек, дерево с запросами по поддереву, хранение и отдача файлов, вычисляемая
агрегация и вход. Нагрузка — несколько человек, практически нулевая.

Размещение при этом определилось не нагрузкой, а тем, что учитель работает
с нескольких устройств, и тем, что учителей несколько
([ADR-0004](0004-mnogouchitelskaya-rabota.md)): локальное приложение
на компьютере отпадает.

## Решение

- **Java 21, Spring** — серверная часть.
- **Thymeleaf** в том же приложении — интерфейс. Отдельного фронтенда нет.
- **PostgreSQL** — хранилище данных.
- **Свой VPS** — развёртывание.
- Разработчик пока один, в перспективе возможны другие.

## Причины

- Решающий критерий — на чём разработчик пишет уверенно и быстро: незнакомый
  фреймворк съел бы больше времени, чем вся предметная сложность вместе взятая.
- PostgreSQL закрывает обе нетривиальные вещи штатно: дерево произвольной
  глубины — рекурсивным запросом (при необходимости `ltree`), распределения
  владения — обычными группировками.
- Serverside-рендеринг вместо отдельного клиента: вторая кодовая база на другом
  языке удвоила бы поддержку, а клиент у системы один и свой; отдельный API
  нужен, когда клиентов несколько.

## Отвергнутые альтернативы

### Локальное приложение на компьютере учителя

Отклонена: несколько устройств и несколько учителей делают её тупиковой.

### Отдельный фронтенд (React/Vue) поверх REST API

Отклонена: разработчик по своей оценке во фронтенде не силён. Дала бы более
приятные сложные экраны — дерево с перетаскиванием, поштучное распределение
задач. К вопросу вернутся, если появится соответствующая компетенция; тогда это
будет новое решение.

## Последствия

- Сложные экраны потребуют точечных вставок JavaScript внутри серверных
  страниц: htmx закроет частичные обновления, но дерево с перетаскиванием
  потребует готовой библиотеки.
- Чтобы возможный отдельный фронтенд потом стоил недорого, предметная логика
  держится в слое сервисов, а контроллеры и шаблоны остаются тонкими
  (см. `standards.md`).
- Нужны домен, бэкапы и процедура обновления живой системы — элемент бэклога
  `deployment-backup`.
- Один разработчик — аргумент за скучные решения: одно приложение, одна база,
  никаких очередей и микросервисов.
