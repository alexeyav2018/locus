# ADR-0023. Оснастка сборки — Maven, Liquibase, PostgreSQL в Docker Compose и Testcontainers

## Контекст

[ADR-0020](0020-stek.md) выбрал стек — Java 21, Spring, Thymeleaf, PostgreSQL,
VPS, — но оставил незакрытыми три вещи, без которых нельзя написать ни строки
кода: чем собирать, чем вести миграции схемы и откуда брать базу при разработке
и в тестах. Карточка `project-skeleton` в `openspec/backlog.md` называет первые
две развилками «за разработчиком», третью не называет вовсе.

Отложить выбор нельзя: каркас строится один раз, и всё последующее ложится
на него. Стоимость пересмотра у трёх решений разная. Систему сборки поменять
позже неприятно, но механически. Инструмент миграций — дорого: к тому моменту
за ним будет история изменений схемы, накопленная всеми элементами бэклога
от `rubricator-tree` до `mastery-views`, и переносить её означает переписывать
заново. Источник базы дешевле всего, но именно он определяет, проверяется ли
признак готовности «миграции применяются с нуля на пустой базе» машиной
или памятью разработчика.

## Решение

- **Maven** — система сборки.
- **Liquibase** — миграции схемы. Схема меняется только ими
  (`standards.md`, раздел «Данные»).
- **Миграции описываются абстрактными операциями Liquibase в YAML**
  (`createTable`, `addColumn`, `createIndex`), а не сырым SQL. Changeset
  с сырым SQL допустим только там, где иначе нельзя, — постгресовые
  расширения, частичные индексы, обходы дерева.
- **PostgreSQL в Docker Compose** — база для локальной разработки, с
  долгоживущим томом.
- **Testcontainers** — база для тестов: чистый контейнер на каждый прогон.

**Откат миграций руками не пишется.** Там, где Liquibase генерирует его сам,
он используется; где не генерирует — не пишется вовсе. Страховка при обновлении
живой системы — архив базы, снятый перед выкаткой, и починка движением вперёд
(новая миграция вместо отката старой). Процедура — элемент бэклога
`deployment-backup`.

Оснастка для тестов апгрейд-пути (теговые changeset'ы `tagDatabase` на границах
версий и базовый класс теста, умеющий остановить Liquibase на теге, засеять
данные и догнать остаток) **сейчас не закладывается**. Она заводится вместе
с первой миграцией, меняющей существующие данные.

## Причины

- **Maven уже стоит на машине разработчика (3.8.7), Gradle — нет; Liquibase
  разработчику знаком, Flyway — нет.** Решающий критерий тот же, что
  и в [ADR-0020](0020-stek.md): на чём разработчик пишет без раздумий.
  Выигрыш Gradle в скорости сборки заметен на проектах, которые больше этого
  на порядок; преимущества Flyway (чистый SQL без промежуточного формата)
  не окупают незнакомого инструмента.
- **Абстрактные операции в YAML дают автоматический откат бесплатно.**
  Для `createTable`, `addColumn`, `createIndex` и подобных Liquibase знает
  обратную операцию и генерирует её сам. Ради этого специально ничего делать
  не нужно — достаточно не писать сырой SQL там, где он не нужен.
- **Testcontainers делает признак готовности «с нуля на пустой базе»
  проверяемым автоматически**, на каждом прогоне тестов, а не тогда, когда
  разработчик вспомнит пересоздать тестовую базу.
- **Долгоживущий том в Compose даёт вторую проверку бесплатно**:
  при каждом запуске приложения Liquibase накатывается инкрементально на базу,
  где уже лежат данные предыдущей версии. Это не тест, но грубые случаи
  (`SET NOT NULL` поверх `NULL`, уникальный индекс поверх дублей) вскрываются
  сразу.
- **Compose воспроизводит окружение VPS** — одна и та же версия PostgreSQL
  локально и в бою; локально установленный постгрес разъезжается с боевым молча.

## Отвергнутые альтернативы

### Gradle

Отклонена не как худшая, а как незнакомая: обе системы для проекта такого
размера равнозначны, и выбор решает привычка. К вопросу вернуться незачем.

### Flyway

Отклонена: у разработчика нет опыта работы с ней, а с Liquibase — есть.
Flyway дал бы чистый SQL без промежуточного формата, что для базы, которая
всегда будет PostgreSQL, выглядит уместнее. Но этот довод меряется временем
на изучение, и в сравнении с ним не выигрывает.

### Сырой SQL как формат миграций (formatted SQL внутри Liquibase)

Отклонена. Выглядит привлекательно — читаешь файл и видишь ровно тот SQL,
который выполнится, — но отключает автоматический откат целиком:
документация Liquibase прямо говорит, что для changeset'ов в формате SQL
обратные операции не генерируются. Абстрактные операции YAML сохраняют
эту возможность, ничего взамен не требуя. Там, где абстракций не хватает,
сырой SQL остаётся как исключение — и там отката просто нет.

### Писать откаты руками там, где они не генерируются

Отклонена: цена не окупается. Откатный скрипт пишется в момент написания
миграции и до боевого применения не выполняется ни разу — то есть с большой
вероятностью сломан именно тогда, когда понадобится. Кроме того, откат
восстанавливает структуру, но не данные: возвращённая после `DROP` колонка
приходит пустой. Проверка `liquibase:updateTestingRollback` этого не ловит —
она удостоверяет обратимость структуры, а не сохранность данных.

Взамен — архив базы перед выкаткой. Он теряет то, что записано после снятия
архива; для системы, где работают один-два учителя, эти минуты приемлемы.

### Локально установленный PostgreSQL вместо Compose

Отклонена: тестовую базу пришлось бы заводить и чистить руками, её состояние
копилось бы между прогонами, а версия базы разъезжалась бы с боевой. Это ровно
то ручное трогание базы, которое запрещает `standards.md`.

### Заложить оснастку тестов апгрейд-пути сразу

Отклонена не по существу, а по сроку: на скелете «предыдущей версии» схемы
не существует, применить оснастку не к чему, и до первого использования она
успеет разойтись с тем, что реально понадобится. Вернуться — с первой
миграцией, меняющей существующие данные; ближайшие кандидаты в бэклоге —
`rubricator-restructure`, `method-edit-impact`, `topic-merge`.

## Последствия

- Тесты стартуют медленнее: первый прогон качает образ PostgreSQL, каждый
  последующий поднимает контейнер. Для проекта этого размера приемлемо.
- Разработка требует запущенного демона Docker. Это новая зависимость среды,
  которой не было у документов.
- Постгресовые вещи — расширения, `ltree` в рубрикаторе, частичные индексы —
  абстракциями Liquibase не выражаются и остаются сырым SQL. В таких
  changeset'ах автоматического отката нет; это ожидаемое исключение,
  а не недосмотр.
- Фактический SQL, который выполнится, из YAML не виден напрямую. Посмотреть
  его перед выкаткой — `liquibase:updateSQL`.
- Обновление живой системы обязано начинаться со снятия архива базы. Без него
  у выкатки нет пути назад вообще. Это входит в `deployment-backup`
  и до него система живёт только локально.
- Апгрейд-путь до появления упомянутой оснастки проверяется только косвенно —
  через долгоживущую базу разработки. Полная репетиция на копии боевой базы
  относится к элементу бэклога `deployment-backup`.
