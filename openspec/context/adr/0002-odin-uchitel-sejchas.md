# ADR-0002. Один учитель сейчас, многоучительская модель данных

## Контекст

Первый работающий экземпляр обслуживает одного конкретного учителя и его
учеников. При этом было понятно, что появление второго учителя когда-нибудь
вероятно, а переделка одноучительской модели в многоучительскую задним числом
означает миграцию всей базы и ревизию каждого запроса.

## Решение

Модель данных сразу проектируется многоучительской: у сущностей учителя
(задача, теория, задание, расписание) с самого начала есть владелец, и любой
запрос за данными учителя фильтруется по владельцу — даже когда владелец один.
UI и логику регистрации второго учителя не делаем.

## Причины

- Поле владельца стоит одну колонку сейчас и миграцию всей базы потом.
- Незакрытый фильтр по владельцу — типовой способ тихо показать одному учителю
  данные другого; привычка фильтровать вырабатывается с первого запроса, а не
  вводится позже.

## Отвергнутые альтернативы

### Жёстко одноучительская модель

Отклонена: экономия почти нулевая, а стоимость обратного хода велика.

### Полноценная многоучительская работа сразу

Отклонена как преждевременная: регистрация, разделение данных и интерфейсы
для второго учителя не нужны, пока учитель один.

## Последствия

Владелец есть у каждой сущности учителя, но в первой версии всегда один и тот
же. Вопрос «общая библиотека задач против личной базы» остался открытым.

## Связи

Заменено [ADR-0004](0004-mnogouchitelskaya-rabota.md): многоучительская работа
понадобилась в первой версии, причём в виде общей библиотеки — то есть
изменилось не только «когда», но и «как». Правило «фильтровать по владельцу
всегда» после этого перестало быть безусловным: к общей библиотеке фильтр
не применяется.
