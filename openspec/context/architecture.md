# Архитектура

**Это по большей части замысел, а не описание существующего.** Построены
каркас (приложение, база, миграции, локальный запуск), вход с ролями,
хранилище файлов — интерфейс `FileStorage` с двумя реализациями, подписанные
ссылки, пережатие изображений — рубрикатор: дерево Разделов и Тем, его
ведение Администратором и обход поддерева — словари Методов
и Характеристик: два плоских общих списка, которые ведёт Администратор
и читают все вошедшие — и каталог Задач: два PDF, номер и подпись, разметка
Темами, Методами, Характеристиками и Частью, первый потребитель хранилища
файлов. Всё, что ниже говорит о теории, учениках, заданиях и владении, —
задумано, но не написано. Документ фиксирует, как система
задумана, чтобы решения не пересобирались заново на каждом изменении.
Что система действительно умеет — в `openspec/specs/`.

Стек и его обоснование — [ADR-0020](adr/0020-stek.md), хранилище файлов —
[ADR-0021](adr/0021-hranilishche-fajlov.md).

## Общая форма

Одно приложение. Ни очередей, ни микросервисов, ни фоновых процессов —
последних нет по существу, а не из экономии: единственное состояние, которое
напрашивалось хранить, оказалось вычислимым
([ADR-0017](adr/0017-net-uvedomlenij.md)).

```
        браузер (учитель, в т.ч. с телефона)
                 |
                 v
   +-------------------------------+
   |  Spring + Thymeleaf           |
   |                               |
   |  контроллеры (тонкие)         |
   |         |                     |
   |         v                     |
   |  сервисы -- вся предметная    |
   |  логика и проверка прав       |
   |     |            |            |
   |     v            v            |
   |  репозитории  FileStorage     |
   +-----|-------------|-----------+
         |             |
         v             v
   PostgreSQL     объектное хранилище
                  (приватный бакет,
                   подписанные ссылки)
```

## Слои

| Слой | Отвечает за | Не содержит |
| --- | --- | --- |
| Контроллеры | разбор запроса, выбор шаблона | предметной логики, проверок прав |
| Сервисы | предметную логику, права, фильтр по владельцу | деталей HTTP и разметки |
| Репозитории | доступ к данным | решений о том, что кому видно |
| `FileStorage` | файлы: положить, ссылка, удалить | знания о задачах и работах |
| Шаблоны | отображение | вычислений и условий сложнее показа |

Контроллеры и шаблоны тонкие не из эстетики: если позже появится отдельный
фронтенд, это должно быть добавлением контроллеров поверх той же логики,
а не выковыриванием логики из шаблонов.

## Хранение данных

PostgreSQL. Схема — только через миграции; ручная правка базы исключена.

**Дерево рубрикатора** — единственное нетривиальное место. Обход поддерева
нужен постоянно (поиск задач, распределения владения), поэтому способ хранения
выбран под него: **связь «родитель» плюс рекурсивный запрос** (`WITH RECURSIVE`
вниз по `parent_id`, с ограничением глубины). Поддерживать нужно одно поле
`parent_id`, и перемещение узла есть изменение одной строки — никакое поддерево
при этом не переписывается.

Отвергнуты оба альтернативных способа, и по одной и той же причине.
**Материализованный путь** (`/1/7/23/`) требует переписать путь у всего
поддерева при каждом перемещении; недовыполненная перезапись оставляет узлы
с прежним путём, и ошибка тихая — узлы существуют, а обход их не находит.
Выигрыш (обход обычным `LIKE` вместо рекурсии) на сотнях узлов не заметен.
**`ltree`** наследует ту же проблему и добавляет свою: расширение ставится
сырым SQL в миграции, у которой нет отката, и привязывает схему к одной СУБД
глубже, чем сейчас нужно.

Способ единственный на проект — см. [standards.md](standards.md), «Данные».

**Распределения владения** — обычные группировки по статусу. Объёмы малы,
кэширование не требуется.

## Файлы

Два потока с разными свойствами:

| Поток | Кто грузит | Объём | Чувствительность |
| --- | --- | --- | --- |
| PDF задач и теории | Администратор | небольшой, растёт медленно | решения не должны попасть к ученикам |
| Сканы работ | Учитель, часто с телефона | сотни изображений в неделю | персональные данные детей |

Оба — через `FileStorage`, в приватный бакет, наружу только временные
подписанные ссылки. Изображения пережимаются при загрузке.

Реализаций две: объектное хранилище для работы и папка на диске для
разработки. Ссылку подписывают обе — папка своим адресом отдачи, открытым
без входа, потому что пропуском служит подпись, а не сеанс. Иначе требование
«без подписи файл не отдаётся» проверялось бы только у одного варианта,
и проверялся бы при этом не тот, что пойдёт в бой. Пережатие живёт **вне**
`FileStorage`: пережимать надо снимок, но не PDF, а знание о том, что за файл
пришёл, у хранилища отсутствует по этой же таблице слоёв.

## Права доступа

Проверяются в сервисном слое, на каждой операции и на каждом объекте. Роли —
набор прав, а не режим: пользователь входит один раз и получает объединённый
функционал ([ADR-0005](adr/0005-roli-administrator-uchitel.md)).

Главная асимметрия, которую легко нарушить: **фильтр по владельцу применяется
только к личным данным**. Библиотека (рубрикатор, словари, задачи, теория)
отдаётся всем. Обе возможные ошибки тихие — механически применённый к
библиотеке фильтр сделает её пустой, забытый на личных данных покажет чужих
учеников. См. `antipatterns.md`.

## Развёртывание

Свой VPS. Нужны домен, резервное копирование базы **и** файлов, процедура
обновления живой системы. Отдельный элемент бэклога `deployment-backup` —
до него система запускается локально.

**Обновление идёт с остановкой**: остановили систему → сняли архив базы →
накатили миграции → подняли новую версию ([ADR-0024](adr/0024-obnovlenie-s-ostanovkoj.md)).
На этом порядке держатся два свойства сразу. Архив снимается с базы, в которую
никто не пишет, поэтому возврат из него ничего не теряет. И миграции не обязаны
быть обратно совместимыми — старой версии в момент наката не существует.
Откатных скриптов в проекте нет ([ADR-0023](adr/0023-osnastka-sborki.md)):
путь назад даёт архив, а не откат.

### Локальный запуск

База разработки — PostgreSQL в контейнере, описанный `compose.yaml` в корне
репозитория. Приложение **поднимает её само** при запуске и **само** получает
параметры подключения: отдельного шага «сначала запусти базу» нет, и забыть
его нельзя.

**Гасит базу не приложение, а человек** (`docker compose down`). Поведение
по умолчанию — обратное: контейнер останавливает тот экземпляр приложения,
который его поднял. Пока экземпляр один, разницы нет; но если рядом окажется
второй (запущенный на другом порту — обычная случайность при разработке),
остановка первого убирает базу из-под работающего второго. Тот продолжает
отвечать и узнаёт о случившемся не в момент причины, а при первом обращении
к данным — то есть ошибка тихая.

Данные лежат в именованном томе и переживают перезапуск. Это не удобство,
а проверка: каждая новая миграция накатывается на базу, где уже есть данные
предыдущей версии, — единственное, что до `deployment-backup` вообще проверяет
апгрейд-путь. Снося том, эту проверку теряют.

Тесты базу разработки не трогают: они поднимают собственный чистый контейнер
на каждый прогон.

В бою всё это не возникает: экземпляр приложения один ([ADR-0020](adr/0020-stek.md)),
и на этом же стоит порядок обновления с остановкой.

## Внешние зависимости

Одна: объектное хранилище. При его недоступности не открываются файлы,
но остальная система работает. Ничего другого наружу система не вызывает —
ни почты, ни мессенджеров, ни платежей.
