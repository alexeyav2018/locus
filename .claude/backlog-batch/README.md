# Батч бэклога

Периодический прогон `openspec/backlog.md`: таймер раз в полчаса запускает
**цикл**. Цикл поднимает сессию Claude Code, та работает над **одним**
элементом очереди — доводит его до слияния в `develop` либо продвигает
настолько, насколько хватает контекста, — и завершается. Цикл смотрит
очередь: есть что брать — сразу поднимает следующую сессию, и так не больше
десяти раз за запуск. Что именно делать, сессия по-прежнему решает сама —
по таблице порядка и состоянию репозитория; цикл лишь решает, поднимать ли её.

## Управление

```bash
.claude/backlog-batch/locus-backlog start    # включить периодические запуски
.claude/backlog-batch/locus-backlog stop     # выключить расписание
.claude/backlog-batch/locus-backlog status   # что сейчас происходит
.claude/backlog-batch/locus-backlog attach   # подключиться к живой сессии
.claude/backlog-batch/locus-backlog kill     # прервать текущую сессию и цикл
.claude/backlog-batch/locus-backlog next     # что взяла бы следующая сессия
```

`stop` останавливает **расписание**, а не текущую работу: начатая сессия
доигрывает до конца, но новой цикл уже не поднимает. Прервать сразу — `kill`:
он гасит и цикл, и сессию, незакоммиченное останется в рабочем дереве как есть.

История запусков — `journalctl --user -u locus-backlog.service`.

## Как это устроено

| Часть | Где | Что делает |
| --- | --- | --- |
| расписание | `~/.config/systemd/user/locus-backlog.timer` | `OnCalendar=*:2/30`, круглосуточно |
| запуск | `~/.config/systemd/user/locus-backlog.service` | зовёт `locus-backlog run`, `TimeoutStartSec=infinity` |
| скрипт | `locus-backlog` | управление, цикл сессий, подъём сессии в tmux |
| задание | `task-prompt.md` | что сессия делает; версионируется вместе с проектом |
| правило вопросов | `question-policy.md` | когда спрашивать владельца; идёт через `--append-system-prompt-file` |

**Замок — имя tmux-сессии `locus-backlog`.** `tmux new-session` отказывается
создать сессию с занятым именем, и очередной запуск таймера выходит на первой
же команде: Claude при этом не стартует, ни токена не тратится. Отдельного
файла-замка нет и не нужно — имя освобождается ровно тогда, когда процесс
закончился.

## Цикл

`locus-backlog run` — цикл до `MAX_RUNS=10` сессий:

1. есть ли что брать? Нет — цикл окончен, Claude не стартует;
2. поднять сессию в tmux и ждать, пока она освободит замок (опрос раз в 30 с);
3. сессия ничего не закоммитила — цикл окончен; расписание остановлено
   (`stop`) — цикл окончен; иначе — к шагу 1.

**«Есть что брать»** вычисляется тем же правилом, что у сессии в «Шаге 0»
`task-prompt.md`: активное изменение в `openspec/changes/` либо строка таблицы
порядка с пустым «Статусом», у которой все зависимости с ✅. Зависимость,
которой в таблице нет (`project-skeleton`, `rubricator-tree`), выполнена,
если её изменение лежит в архиве. Посмотреть ответ — `locus-backlog next`.

**Стоп по «ничего не закоммитила»** — защита квоты. Сессия, сделавшая хоть
что-то, обязательно коммитит (раздел, слияние, пометка строки при отказе).
Если ни одна ветка не сдвинулась, значит сессия упёрлась во что-то, чего
следующая не обойдёт, — например, цикл и сессия разошлись в оценке очереди.
Десять холодных стартов подряд на одном и том же стоили бы дорого.

Служба `Type=oneshot` живёт, пока идёт цикл, — часами, если сессия ждёт
ответа владельца, поэтому `TimeoutStartSec=infinity`. Пока служба активна,
таймер её повторно не запускает: это второй замок поверх имени tmux-сессии.

Сам скрипт лежит в рабочем дереве, и сессии меняют его, переключая ветки,
пока цикл работает. Поэтому `esac; exit $?` стоит одной строкой: bash
разбирает строку целиком и выходит, а не дочитывает новую версию файла
с прежнего смещения.

**`KillMode=process` в юните обязателен.** По умолчанию systemd после
завершения `ExecStart` гасит всё, что осталось в контрольной группе, —
включая только что порождённый tmux-сервер. Отказ выглядит как успех:
служба рапортует «запущена задача», в журнале ни одной ошибки, а сессии
нет. Первый запуск батча 10.09.2026 умер именно так.

## Принятые решения

Все — решения владельца, принятые при постройке 09.09.2026.

| Что | Как |
| --- | --- |
| расписание | круглосуточно; квоту батч делит с владельцем |
| цикл | раз в полчаса; до десяти сессий подряд, пока в очереди есть что брать (08.10.2026) |
| остановка, обязательная | новая запись журнала ADR на любом шаге: владелец видит решение до того, как сессия пойдёт дальше (06.10.2026) |
| остановки прочие | только развилка, где у сессии нет предпочтительного варианта; если уверенный предпочтительный есть — выбирает сама и записывает след (06.10.2026) |
| приоритет | правило вопросов `question-policy.md` передаётся системным промптом и главнее указаний навыков |
| после обрыва по квоте | продолжать с первого `[ ]` в `tasks.md`, **без** предварительной сборки |
| нарезка реализации | один раздел `tasks.md` за сессию, без оценок контекста |
| ломающие строки бэклога | брать как обычные, не спрашивая заранее |
| ветка | `backlog/<id>`, **не удаляется** — архив того, как задача решалась |
| коммит и пуш | перед **каждым** вопросом владельцу, снимками `wip: …` |
| уведомление | явным вызовом `PushNotification`, а не в надежде на харнесс |
| слияние | одним коммитом в `develop` при архивации |

Смысл пуша перед вопросом: владельцу приходит уведомление, он открывает
GitHub с телефона и смотрит артефакты. Не отправлено — уведомление бесполезно.

Смысл нарезки: главный расход — не холодный старт, а длина контекста,
помноженная на число ходов. В `apply` ходов сотни, и каждый платит долю
от всего накопленного; переполнение вдобавок вызывает сжатие, которое
обнуляет кэш. Резать по разделам `tasks.md` дешевле, чем тянуть одну
сессию до конца, и — в отличие от нарезки по фазам с одобрением через
Pull Request — не стоит ни одного живого вопроса владельцу: гейт и все
развилки остаются диалогом в живой сессии.

Порога по заполненности контекста нет намеренно. Изнутри сессии контекст
измерить нечем: `/context` набирает человек, а размер собственного
транскрипта (`$CLAUDE_CODE_SESSION_ID`) — мера косвенная, байты к токенам
относятся по-разному в зависимости от доли вывода команд. Правило «один
раздел за сессию» от измерений не зависит вовсе. Плата — холодный старт
на каждый раздел; она меньше, чем экономия на коротком контексте.

Простоя между разделами нет вовсе: следующую сессию поднимает цикл сразу
после выхода предыдущей (08.10.2026; до того — таймер раз в десять минут,
и раздел ждал очередного тика). Таймер раз в полчаса нужен только для
того, чтобы начать новый цикл — после десяти сессий, после остановки
по «ничего не закоммитила» или когда в очереди появилось что брать.

## Разовая настройка

Две вещи делаются руками один раз и в репозитории не живут.

**Deploy key.** Батч пушит ключом `~/.ssh/locus_backlog` — отдельным, без
пароля, потому что таймер срабатывает и тогда, когда владелец не залогинен
и GNOME keyring не поднят. Ключ надо добавить в репозиторий с правом записи:

```bash
gh repo deploy-key add ~/.ssh/locus_backlog.pub \
   --title "locus-backlog" --allow-write -R alexeyav2018/locus
```

Именно deploy key, а не аккаунтный ключ: утечка файла даёт запись в один
приватный репозиторий, а не доступ ко всему GitHub.

**Linger.** Без него пользовательские таймеры не работают, пока владелец
не залогинен, и круглосуточность окажется мнимой:

```bash
loginctl enable-linger vorotovalexey
```
