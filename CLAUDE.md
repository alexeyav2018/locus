## Продукт

Платформа поддержки учителя математики. Заявленные учителем сценарии (со слов заказчика,
формулировки предварительные):

- собирать и систематизировать задания;
- вести учёт теоретических материалов;
- выдавать задания школьникам и принимать от них ответы;
- выстраивать расписание учителя.

## Принятые решения

### Школьник — полноценный пользователь системы (решено 2026-09-04)

Школьники заходят в систему сами: видят выданные им задания, отправляют ответы.
Это значит, что мы строим **веб-сервис, доступный из интернета**, а не локальный
инструмент на компьютере учителя. Из этого автоматически следует набор обязательных
задач, которые нельзя отложить «на потом»:

- учётные записи и вход для двух ролей — учитель и школьник;
- права доступа: школьник видит только свои выдачи и не видит ответы к несданному,
  чужие работы ему недоступны;
- хостинг, домен, бэкапы, обновление живой системы;
- хранилище для присланных школьниками файлов (если решения отправляют фотографиями);
- поведение системы во времени: сроки сдачи, опоздания, кто и когда может править ответ.

Роли администратора и родителя пока не обсуждались.

### Один учитель сейчас, много учителей потом (решено 2026-09-04)

Первый работающий экземпляр обслуживает одного учителя и его учеников, но модель данных
сразу проектируется многоучительской. Практические следствия для кода:

- у сущностей учителя (задача, теория, задание, расписание) с самого начала есть
  владелец; в первой версии он всегда один и тот же, но поле существует;
- любой запрос за данными учителя фильтруется по владельцу — даже когда владелец один.
  Это привычка, а не оптимизация: именно незакрытый фильтр потом тихо показывает
  учителю А данные учителя Б;
- UI и логику регистрации второго учителя пока не делаем;
- вопрос «общая библиотека задач против личной базы» отложен, но модель не должна
  ему противоречить.

## Словарь предметной области (черновой)

Термины ещё не утверждены — при первом же обсуждении их надо закрепить и потом
использовать одинаково в коде, в UI и в разговоре.

- **Задача** — отдельная математическая задача с условием и (возможно) решением/ответом.
- **Задание** — то, что выдаётся школьнику; вероятно, набор задач + срок + адресат.
- **Теоретический материал** — текст/формулы/ссылки, привязанные к теме.
- **Выдача** — факт назначения задания конкретному школьнику или группе.
- **Ответ** — присланное школьником решение и его проверка.
- **Расписание** — занятия учителя во времени.

Открытый вопрос по каждому термину: как он связан с остальными (например, живёт ли
задача внутри задания или существует независимо и переиспользуется).

## Процесс: OpenSpec

Проект ведётся спекой вперёд кода. Инструмент — OpenSpec (`@fission-ai/openspec`,
запускается через `npx -y @fission-ai/openspec@latest`, короткое имя `openspec`).

Структура:

- `openspec/specs/` — действующие спецификации системы (истина о том, что уже есть);
- `openspec/changes/<имя>/` — предложение изменения: зачем, требования, задачи;
- `openspec/changes/archive/` — выполненные изменения;
- `openspec/config.yaml` — схема `spec-driven` и правило языка.

**Язык артефактов — русский**, но структурные заголовки OpenSpec и ключевые слова
`SHALL`/`MUST` остаются английскими: по ним идёт валидация (`openspec/config.yaml:3`).

Рабочий цикл — слэш-команды из `.claude/commands/opsx/` (инструкции к ним лежат
в `.claude/skills/openspec-*/SKILL.md`):

| Команда | Что делает |
| --- | --- |
| `/opsx:explore` | разобраться в задаче до написания предложения |
| `/opsx:propose "идея"` | создать новое изменение в `openspec/changes/` |
| `/opsx:update` | доработать уже созданное предложение |
| `/opsx:apply` | реализовать изменение по его задачам |
| `/opsx:sync` | привести спеки в соответствие с кодом |
| `/opsx:archive` | закрыть изменение и обновить `openspec/specs/` |

Полезное из CLI:

```bash
openspec list              # список изменений
openspec list --specs      # список спецификаций
openspec validate          # проверить корректность спек и изменений
openspec show <имя>        # показать изменение или спеку
openspec status            # готовность артефактов по изменению
```

Не начинай реализацию в обход этого цикла: сначала предложение, потом код.

## MCP-серверы

Подключены в `.mcp.json` (область — проект, файл коммитится):

- **serena** — семантическая навигация и правка кода через языковые серверы:
  поиск символов, ссылок, точечное редактирование вместо чтения файлов целиком.
  Запускается `uvx` из git-репозитория `oraios/serena`, контекст `ide-assistant`.
  Свой кеш кладёт в `.serena/cache/` (в `.gitignore`). Пока кода нет, пользы от
  него мало — он раскроется, когда появится кодовая база.
- **context7** — актуальная документация библиотек и фреймворков по запросу.
  Нужен именно при выборе стека: не полагайся на память о версиях API, спроси его.

Проектные MCP-серверы требуют однократного подтверждения пользователем при первом
запуске сессии.

## Решения, которые ещё не приняты

Список ведём здесь, чтобы не переоткрывать одни и те же вопросы:

1. Стек: язык, фреймворк, БД, способ развёртывания.
2. Как хранятся и рендерятся математические формулы (LaTeX/MathML/картинки) — это
   влияет на выбор стека сильнее, чем кажется.
3. Модель данных: связи «задача ↔ тема ↔ теория ↔ задание ↔ выдача ↔ ответ».
4. Нужна ли автоматическая проверка ответов или только ручная.
5. Может ли один школьник заниматься у нескольких учителей (когда учителей станет много).
