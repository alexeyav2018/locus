# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Статус: есть каркас, вход, роли, хранилище файлов, перестраиваемый рубрикатор, словари, Задачи с поиском, Теория, Ученики и Группы, Задания, Работы, Отметки Владения, экран Владения, выбытие Ученика, версия системы, сборка и обрезка PDF Задачи, расписание с переносами и отменами Встреч

Построен каркас (`project-skeleton`): приложение на Java 21 и Spring Boot,
Thymeleaf, PostgreSQL, миграции Liquibase, тесты на Testcontainers. Поверх него
`auth-roles` принёс первые доменные таблицы — Пользователя и Роли: вход по
паролю, разграничение по ролям, ведение учётных записей Администратором.
Затем `file-storage` — интерфейс `FileStorage` с двумя реализациями (объектное
хранилище и папка на диске), временные подписанные ссылки и пережатие
изображений.
Затем `rubricator-tree` — рубрикатор: дерево Разделов и Тем произвольной
глубины, его ведение Администратором и обход поддерева.
Затем `library-dictionaries` — словари Методов и Характеристик: два плоских
общих списка «идентификатор и имя», ведение Администратором на одном экране,
уникальность имени без учёта регистра.
Затем `problem-catalog` — Задача: два PDF, номер (Подпись была и убрана
`problem-caption-removal`, [ADR-0050](openspec/context/adr/0050-zadacha-razlichaetsya-tolko-nomerom.md)),
разметка Темами, Методами, Характеристиками и Частью, список Задач
на выбранной Теме и правка до первого использования. Она же дала работу
трём предыдущим: хранилище получило первого потребителя, дерево — содержимое
(Тема с Задачами тогда не удалялась и не углублялась), словари — настоящую проверку
«удаляется только неиспользуемая запись».
Затем `library-search` — поиск по библиотеке: экран `/problems`, где Задачи
отбираются по узлу рубрикатора (вместе со всем его поддеревом), Методам,
Характеристикам и Части. У Методов и у Характеристик учитель выбирает, как
соединять выбранные значения — «все сразу» или «любое из»
([ADR-0031](openspec/context/adr/0031-uslovija-poiska-po-biblioteke.md));
разные условия соединяются по «и» всегда. Библиотека общая, поэтому фильтра
по владельцу здесь нет и быть не должно — это сторожат тесты.
Затем `theory-materials` — Теоретические материалы: название, узел дерева
и содержимое, которым служит либо файл, либо ссылка. Материал крепится
к **любому** узлу — и к Разделу, и к Теме, — а виден на всём его поддереве,
с указанием, откуда пришёл ([ADR-0032](openspec/context/adr/0032-teoriya-na-odnom-uzle-i-nasledovanie.md));
заморозки после использования у теории нет ([ADR-0033](openspec/context/adr/0033-teoriya-ne-zamorazhivaetsya.md)).
Показываются материалы там же, где Задачи, — в правой части экрана дерева.
Ею же погашен второй долг рубрикатора: узел со своими материалами
не удаляется, а углублению материалы не мешают.
Затем `rubricator-restructure` — перестройка дерева: сняты два временных
отказа рубрикатора. Тему с Задачами можно углубить, указав **Тему-приёмник**
(создаваемого потомка либо существующую Тему), и снять **с распределением** —
каждой Задаче своя Тема-приёмник, родитель допустим, если снимаемая Тема
его единственный потомок. Дерево не знает Задач по имени: переезд и
распределение идут через расширенный до действия вопрос `NodeContent`.
Перестройка двигает и замороженную Задачу
([ADR-0034](openspec/context/adr/0034-perestrojka-silnee-zamorozki.md)).
Число исчезающих отметок Владения показывается перед снятием; перенос
и счёт отметок пришли позже с `mastery-marks`.
Затем `students-groups` — первая область личного контура: Ученик (имя
и владелец, без учётной записи — сторожит `StudentIsNotAUserTest`) и Группа
(именованный список Учеников того же Учителя, имя неповторимо у одного
владельца). Ведёт их Учитель, и только свои: у репозиториев нет метода
без `UserId` (`OwnerIsRequiredByStudentsTest`), Учитель не видит чужих
ни одним запросом, а библиотеку видят оба целиком
(`StudentsAreFilteredByOwnerTest`). Ученик удаляется, пока на него ничего
не ссылается, Группа — в любой момент
([ADR-0035](openspec/context/adr/0035-udalenie-uchenika-i-gruppy.md));
на вопрос `StudentUsage` отвечают `assignments`, `submission-review`
и `mastery-marks` — что все три названы, сторожит `StudentUsageDebtTest`.
Затем `assignments` — вторая область личного контура и первая, ссылающаяся
на библиотеку: Задание (набор Задач одному Ученику со сроком и охватом
теории `TheoryScope`) и Раздача (одно действие выдачи Группе; помнит
**имя** Группы текстом, а не ключ — Группа удаляется в любой момент).
Выдача начинается с поиска: Учитель отмечает найденные Задачи на `/problems`
и переходит к форме `/assignments/new`. После выдачи Задание не правится,
кроме переноса срока, и удаляется, пока по нему нет Работы
([ADR-0037](openspec/context/adr/0037-zadanie-neizmenno-posle-vydachi.md)).
«Не сдано» вычисляется от бина `Clock` и вопроса `AssignmentWork`, хранимой
колонки нет (`NotSubmittedIsNotStoredTest`, `NotSubmittedTest` на `TestClock`);
на `AssignmentWork` отвечает `submission-review` — что вопрос и ответчик
названы, сторожит `AssignmentWorkDebtTest`. Здесь же впервые по-настоящему сработали
заморозка Задачи (ADR-0030) и неудаляемость Ученика (ADR-0035): `assignments`
отвечает на `ProblemUsage` и `StudentUsage`. Ответ библиотеке считает
Задания **всех** Учителей — `AssignmentRepository.countByProblem` без
`UserId`, оформлен как класс исключений из ADR-0027
([ADR-0036](openspec/context/adr/0036-voprosy-biblioteki-bez-vladelca.md))
и перечислен поимённо в `OwnerIsRequiredByAssignmentsTest`.

Затем `submission-review` — третья область личного контура и первый
потребитель хранилища в нём: Работа (`StudentWork`) — решение **одной
Задачи одного Задания**: файлы (изображение пережимается, PDF как есть,
прочее отклоняется; хотя бы один), дата получения, вердикт `Verdict`
и примечание. На паре «Задание × Задача» Работа одна, вердикт ставится
отдельно от приёма и меняется свободно (без вердикта — «не проверена»,
это отсутствие данных, а не флаг), Работа удаляется владельцем в любой
момент вместе с файлами
([ADR-0038](openspec/context/adr/0038-rabota-odna-na-paru-i-udalyaetsya-svobodno.md)).
Ученика у Работы нет — он у Задания. Экран приёма `/works?assignment=`
и список Работ Ученика `/works?student=` рассчитаны на телефон; пределы
загрузки заданы в `application.yaml`. У репозитория нет метода без `UserId`
и нет исключений (`OwnerIsRequiredByWorksTest`, `WorksAreFilteredByOwnerTest`).
Здесь впервые по-настоящему сработали «не сдано» по Работе и отказ
в удалении Задания: `submission-review` отвечает на `AssignmentWork`
(`WorksOfAssignment`, `AssignmentWorkAnsweredTest`) и на `StudentUsage`
(`WorksOfStudent`); отказ в удалении Ученика теперь называет все причины
разом.

Затем `mastery-marks` — четвёртая область личного контура и смысловое
ядро: отметка Владения (`Mastery`) — суждение Учителя о своём Ученике
на паре «Тема × Метод», значение из шкалы `MasteryStatus`. Хранится
только текущее значение и только с суждением: `неизвестно` — отсутствие
строки, простановка `неизвестно` строку удаляет; при углублении Темы
отметки переезжают на приёмник и сливаются по ADR-0013, если ячейка
занята; справка «решено N из M» считает только проверенные Работы
([ADR-0039](openspec/context/adr/0039-otmetka-tolko-s-suzhdeniem.md)).
Ставятся на экране приёма `/works?assignment=` по принятой Работе —
ячейки-кандидаты «Темы Задачи × её Методы», выборочно, без
предзаполнения, `POST /mastery`; вердикт на отметки не влияет, Работа
удаляется — отметка остаётся. `MasteryRepository` — с `UserId` всюду,
кроме четырёх методов класса ADR-0036 (`countByTopic`, `countByMethod`,
`rehomeTopic`, `deleteByTopic`), перечисленных поимённо
в `OwnerIsRequiredByMasteryTest`; изоляция — `MasteryIsFilteredByOwnerTest`.
Погашены три долга: дерево (`MasteryOnNode implements NodeContent` —
переезд, исчезновение, настоящий счёт; `MasteryRestructureTest`),
Ученики (`MasteryOfStudent implements StudentUsage` — «вынесено
суждений (N)») и словарь (`MasteryOfMethod implements DictionaryUsage` —
Метод с отметками не удаляется; `MasteryGuardsTheMethodTest`).

Затем `mastery-views` — пятая и последняя работа личного контура редакции 1
стратегии: экран `/mastery` показывает состояние Ученика — распределения
по четырём статусам (`Distribution`) по Теме, по Разделу (складываются
по поддереву) и по Методу (складываются сквозь Темы), и перечень пробелов
(ячейки со статусом «не владеет») со ссылкой в существующий поиск библиотеки
как подбором задач под пробел. Ячейки-кандидаты — Методы из разметки Задач
Темы, объединённые с Методами уже стоящих отметок; узел без ячеек показывает
это явно, а не нулевое распределение. Единого числового значения владения
по-прежнему нет нигде — только распределения ([ADR-0013](openspec/context/adr/0013-agregaciya-raspredelenie.md)),
что проверяет `NoSingleMasteryValueTest`. Экран только читает: ни одной формы
на нём нет ([ADR-0011](openspec/context/adr/0011-otmetka-na-pare.md)). Вопрос
библиотеки `findMethodsUsedByTopic` — без владельца, классом ADR-0036, как
и остальные вопросы к общей библиотеке.

Затем `student-withdrawal` — закрытый ADR-0035 долг: Ученик получил
состояние **выбыл**/**действует** (`withdrawn`), переключаемое Учителем
в обе стороны свободно и без каскада — Группы, Задания, Работы и Владение
не меняются ([ADR-0040](openspec/context/adr/0040-vybytie-uchenika-flag.md)).
Список `/students` по умолчанию показывает только действующих, выбывшие —
по явному запросу тем же экраном; карточка выбывшего и вся его история
остаются доступны без ограничений. Прямая выдача выбывшему отклоняется,
и он не предлагается в форме; Раздача Группе пропускает выбывших членов,
отклоняясь только если действующих не осталось.

Затем `ui-redesign` — новый интерфейс при прежней архитектуре: единая
система оформления (`static/css/locus.css`), общий каркас с шапкой
(`templates/fragments/shell.html`, данные — `ShellAdvice`), цветом разведены
общее и личное, главная учителя начинается с несданных Заданий, Владение
показано полосами распределения. Концепция — `openspec/context/ux-concept.md`,
решение — [ADR-0041](openspec/context/adr/0041-edinaya-sistema-oformleniya.md).
Свои `<style>` и встроенные скрипты в шаблонах не заводятся.

Затем `interface-focus` — порядок на экране и навигация без браузера:
вторичное (правка, перенос, удаление, замена файлов, заведение) — под
раскрывающимися блоками на той же странице, при отказе сервиса раскрыт блок
именно этого действия; «Отмена» в формах; контекстный возврат параметром `from`
(`ReturnTo` пропускает только внутренние адреса); свои страницы ошибок
403/404/500; просмотр файлов внутри системы (`file/viewer.html`); «Выйти»
в шапке ([ADR-0042](openspec/context/adr/0042-vtorichnoe-po-knopke-i-vozvrat.md)).
Встроенный просмотр PDF на телефонах ненадёжен — у него запасная кнопка.

Затем `versioning` — версия системы: чистая `X.Y.Z` в `pom.xml` (без
`-SNAPSHOT`), уровень каждое изменение решает само в `proposal.md`,
последним пунктом `tasks.md` поднимает версию и дописывает `CHANGELOG.md`,
а коммит архивации получает аннотированный тег `vX.Y.Z`, который сразу
отправляется в `origin`. Правила уровней — `standards.md`, раздел «Версии»,
решение — [ADR-0043](openspec/context/adr/0043-versionirovanie-sistemy.md).
Версия и короткий хеш коммита видны в подвале каждой страницы, в том числе
у посетителя без входа (`EveryPageShowsTheVersionTest`). Первая версия —
`1.0.0`, с выкладкой на стенд она не связана; `MAJOR` растёт при крупных
изменениях (новый интерфейс, большая возможность).

Затем `problem-pdf-assembly` — работа за пределами редакции 1
стратегии, задним числом вписанная вехой 1 редакции 2
([ADR-0046](openspec/context/adr/0046-redakciya-2-strategii-raspisanie.md)):
каждый из двух PDF Задачи Администратор прикладывает готовым либо **собирает** из картинок (JPEG, PNG) и диапазонов целых страниц
загруженных PDF — при заведении и при замене файла
([ADR-0044](openspec/context/adr/0044-sborka-pdf-zadachi.md)). Сборка —
чистая функция `PdfAssembly` на PDFBox 3: страница переносится целиком,
без интерпретации содержимого, с ресурсами только взятых страниц; картинка —
страница своего размера, без пережатия. Исходник живёт **Черновиком сборки**
(`AssemblyDraft`) — строка в базе и файл в рабочей папке мимо
`FileStorage`, принадлежит загрузившему; репозиторий с `UserId` всюду,
кроме двух уборок класса ADR-0036 (`OwnerIsRequiredByDraftsTest`).
Брошенные черновики убираются попутно — при открытии инструмента по сроку
и все при старте, без фоновых процессов. Предел загрузки двухуровневый:
контейнер пропускает размер сборника, общий предел держит
`UploadLimitInterceptor` везде, кроме обработчиков с `@LargeUpload`.
У слота одно поле файла: выбранный и не тронутый PDF ложится в Задачу
байт в байт, без пересборки, а диапазоны, рамки и картинки собираются;
без скрипта то же поле прикладывает готовый файл, и принимается только PDF
([ADR-0049](openspec/context/adr/0049-odno-pole-fajla-na-slot-zadachi.md)).

Затем `problem-pdf-crop` — обрезка в той же сборке: на странице источника
Администратор обводит **Рамкой** (`CropFrame`, доли показанной страницы)
нужный кусок мышью или пальцем, либо берёт страницу целиком; с одной
страницы можно взять несколько кусков, не взятая страница в результат
не попадает. Способ обрезки система выбирает сама по каждой странице
([ADR-0045](openspec/context/adr/0045-obrezka-kuska-stranicy.md)):
векторная страница обрезается сужением видимой области и остаётся
векторной — **скрытое за рамкой остаётся в файле**, это принятый риск,
а не дефект; скан (одна картинка и нет текста) и снимок режутся растром,
скан — на 300 dpi. Страницу черновика для рамки показывает сервер
картинкой, отрисованной тем же PDFBox (`GET /problems/drafts/{id}/pages/{page}`),
рамку ставит точечный скрипт из общего `locus.js`; без скрипта целые
страницы и диапазоны собираются по-прежнему.

Затем `schedule` — веха 2 редакции 2 стратегии, новая область личного
контура: **Занятие** (`Lesson`) — хранимое правило встреч Учителя ровно
с одним своим Учеником или одной своей Группой: дата первой встречи, время,
длительность и вид — разовое или еженедельное, у еженедельного может быть
последняя дата. **Встречи** (`Meeting`) не хранятся, а вычисляются чистой
функцией `Meetings.between`; правка еженедельного Занятия действует с даты
и при прошлых Встречах делит его на два
([ADR-0047](openspec/context/adr/0047-zanyatie-pravilo-vstrechi-vychislyayutsya.md)).
Неделя — `/schedule?week=`, дни столбцом под телефон; Встречи сегодняшнего
дня — на главной. Свой адресат держат составные ключи в базе;
`LessonRepository` — с `UserId` всюду и без исключений
(`OwnerIsRequiredByLessonsTest`, `LessonsAreFilteredByOwnerTest`).
`schedule` — четвёртый ответчик `StudentUsage` (`LessonsOfStudent`):
Ученик с Занятием не удаляется; Группа удаляется по-прежнему в любой момент
и уносит свои Занятия каскадом, о чём предупреждает форма. Выбывшему новое
Занятие не назначается, прежние помечены «выбыл».

Затем `schedule-changes` — веха 3 редакции 2: **Поправка Встречи**
(`MeetingAdjustment`) — хранимое исключение из правила на паре «Занятие ×
плановая дата»: отмена, перенос (дата, время, длительность) и неявка;
«как по правилу» — отсутствие строки
([ADR-0048](openspec/context/adr/0048-popravka-vstrechi-na-pare-zanyatie-data.md)).
У каждой Встречи своя страница `/schedule/lessons/{id}/meetings/{дата}`
с действиями; неделя показывает отменённую Встречу с пометкой,
перенесённую — на новом месте (в том числе из другой недели), а на плановой
дате — строку «перенесена на …». Неявка — только у Встречи с Учеником
и только у наступившей; Встреча с неявкой не уезжает в будущее, отмена её
не стирает. Правка Занятия с даты забирает Поправки в новую часть и снимает
Поправки дат, которых правило больше не даёт; удаление Занятия уносит их
каскадом. `MeetingAdjustmentRepository` — с `UserId` всюду и без исключений,
чужое Занятие держит составной ключ.

**Не считай, что что-то из описанного реализовано.** Документы контекста
описывают замысел; что система действительно умеет — только `openspec/specs/`,
а там пока шестнадцать возможностей: `application-startup`, `users-and-roles`,
`file-storage`, `taxonomy`, `library-dictionaries`, `problem-catalog`,
`library-search`, `theory-materials`, `students-groups`, `assignments`,
`submission-review`, `mastery-marks`, `mastery-views`, `interface-navigation`,
`problem-pdf-assembly` и `schedule`.

### Первый вход

Первый Администратор заводится миграцией: имя входа `admin`, пароль `admin`.
Пароль помечен подлежащим смене, и до смены учётной записи не доступно ничего,
кроме формы смены пароля ([ADR-0026](openspec/context/adr/0026-vhod-i-pervyj-administrator.md)).

**Заведите вторую учётную запись с ролью Администратора.** Восстановление
доступа завязано на живого Администратора: если единственный потеряет пароль,
вернуть доступ можно будет только правкой базы руками — в обход правила
«схема и данные меняются миграциями». Технического решения здесь нет
и не планируется.

## Продукт

Платформа поддержки учителя математики. **Система — рабочий инструмент учителя;
ученик в ней не пользователь, а объект учёта.** Взаимодействие с учеником
целиком происходит вне системы.

Заявленные заказчиком сценарии и их судьба:

| Сценарий | Состояние |
| --- | --- |
| собирать и систематизировать задачи | в первой версии |
| вести учёт теоретических материалов | в первой версии |
| выдавать задания и вести учёт ответов | в первой версии, но выдача и приём — вне системы |
| выстраивать расписание учителя | горизонт редакции 2 стратегии ([ADR-0046](openspec/context/adr/0046-redakciya-2-strategii-raspisanie.md)): вехи 2 и 3 построены (`schedule`, `schedule-changes`) |

Смысловое ядро: учитель ведёт **общую библиотеку размеченных задач** и по
каждому ученику знает, **какими методами в каких темах тот владеет**.

## Доменный инвариант: граница общего и личного

Главное, что защищает проект от тихой поломки. **Любое предложение обязано
явно сказать: где живут его данные — в общей библиотеке или в личном контуре
учителя, кто имеет право их менять и фильтруются ли они по владельцу.**

```
   ОБЩЕЕ (под Администратором)         ЛИЧНОЕ (у каждого учителя)
   ---------------------------------   ----------------------------
   рубрикатор: Разделы и Темы          Ученики, Группы
   словари Методов и Характеристик     Задания и сроки
   Задачи (два PDF + разметка)         Работы: сканы и вердикты
   Теоретические материалы             Отметки Владения
```

Фильтр по владельцу применяется **только к правой колонке**. Применённый
к библиотеке — сделает её невидимой; забытый на личных данных — покажет
учителю чужих учеников. Обе ошибки тихие.

- Выбытие Ученика — флаг на карточке, переключаемый свободно, без каскада на Группы; Раздача пропускает выбывших членов ([ADR-0040](openspec/context/adr/0040-vybytie-uchenika-flag.md)).

## Процесс: OpenSpec

Проект ведётся спекой вперёд кода. Инструмент — OpenSpec (`@fission-ai/openspec`,
запускается через `npx -y @fission-ai/openspec@latest`, короткое имя `openspec`).

Структура:

- `openspec/specs/` — действующие спецификации системы (истина о том, что уже есть);
- `openspec/changes/<имя>/` — предложение изменения: зачем, требования, задачи;
- `openspec/changes/archive/` — выполненные изменения;
- `openspec/context/` — документы проекта: словарь, модель, сценарии,
  архитектура, журнал решений, стандарты;
- `openspec/backlog.md` — приоритизированная очередь работ;
- `openspec/config.yaml` — схема `spec-driven`, правило языка, маршрутизация
  по документам контекста.

**Язык артефактов — русский**, но структурные заголовки OpenSpec и ключевые слова
`SHALL`/`MUST` остаются английскими: по ним идёт валидация (`openspec/config.yaml:3`).

Рабочий цикл — слэш-команды из `.claude/commands/opsx/` (инструкции к ним лежат
в `.claude/skills/openspec-*/SKILL.md`):

| Команда | Что делает |
| --- | --- |
| `/opsx:explore` | разобраться в задаче до написания предложения |
| `/opsx:propose "идея"` | создать новое изменение в `openspec/changes/` |
| `/opsx:update` | доработать уже созданное предложение |
| `/opsx:apply` | реализовать изменение по его задачам |
| `/opsx:sync` | привести спеки в соответствие с кодом |
| `/opsx:archive` | закрыть изменение и обновить `openspec/specs/` |

Полезное из CLI:

```bash
openspec list              # список изменений
openspec list --specs      # список спецификаций
openspec validate          # проверить корректность спек и изменений
openspec show <имя>        # показать изменение или спеку
openspec status            # готовность артефактов по изменению
```

Не начинай реализацию в обход этого цикла: сначала предложение, потом код.

### Ведение бэклога

Метод описан в навыке `backlog-maintenance` — он единственный источник правил
(формат карточек, порядок, процедуры). Здесь только особенность проекта:
очередь состоит в основном из работ по постройке, и порядок задают не ключи
сортировки, а **две колонки дуг** — «Зависимость» (без этого не построить)
и «Не позже» (после этого поздно или дорого). Допустим любой порядок, дуг
не нарушающий; класс `Л/Б/Т/Д`, стоимость и ломающесть лишь предпочитают среди
допустимых. Дуга записана только в таблице: в карточках её нет.
Подробности — в разделах 1 и 2 самого `openspec/backlog.md`.

### Журнал решений

Записи `openspec/context/adr/` **неизменяемы**. Изменилось решение — пишется
новая запись, у старой правятся только `status` и `superseded_by`. После любой
правки журнала прогнать:

```bash
python3 openspec/context/adr/build_index.py          # пересобрать индекс
python3 openspec/context/adr/build_index.py --check  # только проверить
```

Скрипт проверяет нумерацию, статусы и двусторонность связей между записями.

### Документы проекта — исходники

`openspec/context/` и сам `CLAUDE.md` — **исходники проекта наравне с кодом**,
а не сопроводительные заметки. Правка, меняющая **смысл**, идёт через цикл
изменений; правка формулировки — попутно:

| Через цикл | Попутно, без цикла |
| --- | --- |
| термин, инвариант, не-цель | формулировка, опечатка |
| горизонт, предпосылка, порядок вех | уточнение примера, битая ссылка |

У изменения, правящего только документы, может не быть дельты спек — тогда
в его `.openspec.yaml` ставится `skip_specs: true`.

`openspec/context/strategy.md` версионируется редакциями: редакция не правится
по частям, а заменяется целиком, прежняя уезжает в
`openspec/context/strategy-archive/`. Действующий горизонт, предпосылки и
условия истечения — в самом документе, здесь они не пересказываются.

`openspec/config.yaml` — оснастка, а не исходник: правится напрямую.

Основание — [ADR-0022](openspec/context/adr/0022-kontekst-kak-ishodniki.md).

### Как пользоваться serena

**Работаешь с исходным кодом — в первую очередь serena, оболочка только иначе.**
Правило имеет приоритет над любым умолчанием вида «делай через Bash, где он
справляется»: для кода оболочка — запасной путь, а не основной. Исходный код —
это `.java` в `src/`; `openspec/*.md`, YAML, SQL и `pom.xml` кодом в этом смысле
не являются: символьные инструменты по ним ничего не находят, а стоят дороже,
и там работают обычные Read, Grep и оболочка.

По шагам: читать — `get_symbols_overview`, затем `find_symbol`; искать
использования — `find_referencing_symbols`; править — `replace_symbol_body`
и `insert_before_symbol`/`insert_after_symbol`; переименовывать —
`rename_symbol`; удалять — `safe_delete_symbol`; проверять —
`get_diagnostics_for_file`.

`cat`, `grep`, `sed` и heredoc по `.java` — только там, где символьного
инструмента для задачи нет: новый файл целиком, локальные переменные
и параметры (символами не являются), беглая проверка вроде «не осталось ли
упоминаний строки». Не потому, что так быстрее, а потому, что иначе никак.

Правила ниже уточняют это общее. За каждым стоит причина; исчезла причина —
правило пересматривается, а не обходится.

- **Сверху вниз, а не файлом целиком.** Сначала `get_symbols_overview` по файлу,
  затем `find_symbol` с `include_body` — только на том символе, который правда нужен.
- **Перед правкой сигнатуры, переносом или удалением — `find_referencing_symbols`.**
  Правила изоляции держатся на том, что найдены *все* вызовы; пропущенный не падает,
  а тихо отдаёт лишнее.
- **Переименование — `rename_symbol`, удаление — `safe_delete_symbol`.** Ручная
  текстовая замена расходится со словарём ([glossary.md](openspec/context/glossary.md))
  и оставляет висящие ссылки.
- **Текстовая правка не применяется вслепую — там, где она всё же уместна.**
  `sed` и `str.replace` при несовпадении образца молчат: файл остаётся прежним,
  скрипт завершается успешно, сборка зелёная, а правки нет. Либо `Edit`, который
  падает на несовпадении, либо скрипт, сначала проверяющий, что образец найден.
  Компиляция это не ловит: не применённая правка оставляет валидный старый код.
- **Заготовленный текстовый патч не переживает `rename_symbol`.** Переименование
  меняет файл под патчем, и патч тихо не применяется. Переименования идут первыми
  и одним заходом, текстовые правки — после.
- **После каждой правки — `get_diagnostics_for_file`**, а не полная сборка
  в конце работы: проверка дешевле и точнее указывает место, но только пока
  правка одна. Накопленные скопом правки диагностика покажет тем же списком,
  что и сборка, — и причину в нём придётся искать.
- **В `.serena/memories/` не писать, мастер `onboarding` не запускать.**
  Единственный источник правды о проекте — `openspec/context/` и этот файл. Вторая
  копия фактов, которую никто не поддерживает, разъедется с первой молча
  ([ADR-0022](openspec/context/adr/0022-kontekst-kak-ishodniki.md)).
- **Номера строк serena отдаёт от нуля.** В ссылках вида `Foo.java:42` — как в этом
  файле и в ответах владельцу — пересчитывать в нумерацию от единицы.
- **Языковой сервер Java подключён** (`.serena/project.yml`,
  `language_servers: [java]`). Если символьные инструменты отвечают
  `Active language servers: []` — конфигурация поменялась после запуска MCP-сервера,
  и его нужно перезапустить: перечитать её на лету serena не умеет.

## Команды сборки и тестов

**Требование среды: запущенный демон Docker.** База разработки поднимается
из `compose.yaml`, тесты — через Testcontainers. Без Docker сборка падает,
и это сознательно: тест, который молча пропустился, создаёт видимость проверки
([ADR-0023](openspec/context/adr/0023-osnastka-sborki.md)).

| Что | Команда |
| --- | --- |
| Собрать | `mvn clean package` |
| Запустить | `mvn spring-boot:run` |
| Все тесты | `mvn test` |
| Один тест | `mvn test -Dtest=LoginTest` |
| Один метод | `mvn test -Dtest=MigrationsOnStartupTest#migrationsApplyOnEmptyDatabase` |
| Снести базу разработки | `docker compose down -v` |

`mvn spring-boot:run` **сам** поднимает PostgreSQL из `compose.yaml` и сам
передаёт приложению параметры подключения — отдельного шага «сначала запусти
базу» нет, и забыть его нельзя. Приложение отвечает на `http://localhost:8080/`.

**Гасить базу приложение не будет**: после остановки приложения контейнер
продолжает работать, пока его не остановят руками. Это сделано намеренно —
причина в [architecture.md](openspec/context/architecture.md), раздел
«Локальный запуск».

Данные базы разработки лежат в именованном томе и переживают перезапуск: каждая
новая миграция накатывается на базу, где уже есть данные предыдущей версии.
Это бесплатная проверка апгрейд-пути; снося том, вы её теряете.

Тесты идут на **чистом** контейнере, поднятом Testcontainers, а не на базе
разработки. Версия образа PostgreSQL задана в `compose.yaml` и больше нигде:
тесты читают её оттуда (`PostgresImage` в тестовых исходниках).
